## 이 문서의 구조에 대하여 (학습 노트)

실무 기능 명세서는 대체로 아래 흐름을 따른다. 각 절이 왜 있는지 알아두면 남의 명세서를 읽을 때도 편하다.

| 절 | 존재 이유 |
|---|---|
| 범위(Scope) | **"안 만드는 것"을 명시**하는 게 핵심이다. 이게 없으면 개발 중에 요구가 무한히 늘어난다 |
| 용어 정의 | 같은 단어를 서로 다르게 쓰는 사고를 막는다. 실제로 이 프로젝트도 "유저"가 세 가지 뜻으로 쓰이고 있었다 |
| 액터/권한 | 누가 무엇을 할 수 있는지. 권한 설계의 출발점 |
| 기능 요구사항 | ID를 붙여 추적 가능하게 한다. 테스트 케이스와 1:1로 연결된다 |
| 비기능 요구사항 | 성능·보안·운영처럼 "기능은 아닌데 없으면 망하는 것" |
| 미결정 사항 | 모르는 걸 모른다고 적어두는 칸. **비워두면 나중에 잊는다** |

### 표기 규약

| 약어 | 원어 | 의미 |
|---|---|---|
| **FR** | Functional Requirement | 기능 요구사항 |
| **NFR** | Non-Functional Requirement | 비기능 요구사항 (성능·보안·운영) |
| **BR** | Business Rule | 비즈니스 규칙 / 검증 규칙 |
| **OI** | Open Issue | 미결정 사항 |

요구사항 ID는 `FR-{영역}-{번호}` 형식이다. 우선순위는 MoSCoW 기법을 따른다.

- **MUST** — 없으면 서비스가 성립하지 않음
- **SHOULD** — 중요하지만 없어도 동작함
- **COULD** — 여유가 되면

## 1. 개요

### 1.1 목적

개인이 소유·플레이한 게임을 기록하고, 진행 상태·평가·지출을 관리하는 백로그 서비스를 개발한다.

### 1.2 프로젝트 성격

본 프로젝트는 **Spring Boot / JPA 학습을 위한 습작**이다. 상업적 서비스화를 하지 않기로 확정했으며, 이에 따라 다음이 성립한다.

- 저작권·API 상업 이용 약관·개인정보 처리방침 관련 요구사항을 다루지 않는다
- 실사용자는 개발자 본인 1명을 전제로 하되, **구조는 다중 사용자를 가정해 설계**한다 (학습 목적)
- 기능 개수를 늘리기보다 **기술 스펙트럼의 깊이**를 우선한다

### 1.3 학습 로드맵상의 위치

```
① JPA 기본편 핵심 개념   → 대화로 압축 학습
② JPA 활용 1편           → 강의 직접 (남의 완성 프로젝트 관통)
③ 습작 데모 서비스        ← 【본 프로젝트】
④ 실서비스 (Brankit / JADU)
```

본 프로젝트는 **③ 습작 데모 단계**이며, 활용편(남이 설계한 프로젝트)과 실서비스 사이의 **완충지대**다.

- ~~활용 1편에는 "내가 설계하고 부딪히는" 경험이 빠져 있다. 그 공백을 메우는 것이 본 프로젝트의 존재 이유다~~
- DTO 변환·예외 처리·보안·배포는 **따로 배우면 붙지 않고, 돌아가는 코드에 하나씩 얹어야 붙는 주제**다. 그래서 완성된 도메인 위에 단계적으로 쌓는 구성을 취한다
- **"습작 데모까지가 학습, 실서비스부터가 개발"** — 이 경계가 로드맵의 핵심이며, 본 프로젝트는 학습 쪽에 속한다

### 1.5 목표 (Goals)

- G-1. 개인 게임 기록의 완전한 CRUD와 조회/통계
- G-2. 기존 Obsidian 기록의 이전(마이그레이션)
- G-3. 학습 목표 달성: 연관관계 설계, N+1 대응, 트랜잭션 경계, 인증/인가, 외부 API 연동, 파일 업로드, 배치, 배포

### 1.6 비목표 (Non-Goals)

- 상업적 운영 및 수익화
- 소셜 기능 (팔로우, 공유, 댓글, 랭킹)

- 플레이 시간 자동 측정 (Steam 연동 등)

## 2. 용어 정의

| 용어 | 정의 |
|---|---|
| **회원 (Member)** | 로그인하는 서비스 계정 |
| **게임 마스터 (Game)** | 게임 자체의 객관적 정보. 전체 회원이 공유한다. IGDB API에서 가져오거나 수동 등록한다 |
| **백로그 항목 (BacklogEntry)** | 특정 회원이 특정 게임에 대해 갖는 개인 기록. 회원과 게임 마스터를 잇는 조인 엔티티다 |
| **오버라이드 (Override)** | 게임 마스터의 값을 개인이 덮어쓴 값. 값이 있으면 그것을, 없으면 마스터 값을 표시한다 |
| **회차 (Playthrough)** | 한 게임을 처음부터 끝까지(또는 중단까지) 플레이한 1회 단위 |
| **플랫폼 (Platform)** | 게임 유통·계정 체계. Steam, Nintendo, PSN, Xbox, GOG, Epic, 실물 등 |
| **플랫폼 계정 (PlatformAccount)** | **회원이 특정 플랫폼에서 보유한 계정.** 예: Steam의 "Beene", Steam의 "Ryan", Nintendo의 "Beene" |
| **기기 (Device)** | 게임을 실제로 실행한 하드웨어 또는 에뮬레이터. Switch 2, Windows PC, Steam Deck, Mac, Ryujinx 등 |
| **취득 (Acquisition)** | 게임을 손에 넣은 방식·경로·금액 |

> **핵심 구분 1 — 플랫폼 계정 ≠ 사람**
> "Beene", "Ryan"은 **계정 라벨**이다. 한 사람이 Steam 계정 두 개를 가질 수 있고, 같은 이름의 계정이 Steam과 Nintendo에 각각 있을 수 있다. 함께 플레이한 사람에 대한 기록은 **태그**로 처리한다.

> **핵심 구분 2 — 플랫폼 ≠ 기기**
> Steam에서 산 게임을 Windows PC로 할 수도, Steam Deck으로 할 수도 있다. 구매 경로(플랫폼)와 실행 환경(기기)은 별개 축이다.

## 3. 범위

### 3.1 포함 (In Scope)

- 회원 가입/로그인/세션 관리, 이메일 인증, 비밀번호 재설정
- Google OAuth 연동 (계정 연결 방식)
- 회원 탈퇴 및 유예 기간 처리
- 게임 마스터 관리 (IGDB 연동 + 수동 등록)
- 백로그 항목 CRUD 및 개인 오버라이드
- 회차 기록 및 검증
- 플랫폼 계정 및 보유 기기 관리
- 취득 정보 및 구독 관리
- 개인 태그
- 목록 조회 (검색/필터/정렬/페이징)
- 통계 (장르, 기간, 지출, 플레이타임)
- 커버 이미지 업로드 (개인 소유)
- Obsidian YAML 임포트
- 관리자 기능 및 감사 로그
- 변경 이력 및 소프트 삭제
- 배포 (Render + Neon + Vercel)

### 3.2 명시적 제외 (Out of Scope)

| 제외 항목 | 사유 |
|---|---|
| DLC를 독립 게임으로 관리 | 본편의 회차 + **별도 취득 기록**으로 흡수 (v1.3). API 호출도 하지 않음 |
| 시리즈/프랜차이즈 묶음 | 학습 가치 대비 복잡도 과다 |
| 위키형 공동 편집 (편집 이력·롤백·반달 방지) | **단독 프로젝트 규모**. 습작 범위를 초과함 |
| 게임 별칭(aliases) 필드 | 개인 오버라이드 이름이 검색 대상이 되므로 불필요 |
| DLC 등록 대기 큐 / 승인 워크플로 | 관리자 = 개발자 본인. 실익 없음 |
| 카카오 로그인 | OAuth2 비표준이라 커스텀 코드 대비 학습량이 낮음 |
| 지역별 출시일 | 가장 이른 출시일 하나만 사용 |
| 플레이 시간 자동 측정 | 수동 정수 입력으로 대체 |
| 위시리스트 별도 개념 | 미구매 + 미플레이 상태로 판단 |
| "함께 플레이한 사람" 전용 엔티티 | 태그로 대체 |
| 스크린샷/영상 | 파일 저장 인프라가 커버와 동일하므로 마지막 단계에서 재검토 |

## 4. 액터 및 권한

| 액터 | 설명 | 권한 |
|---|---|---|
| **비로그인 사용자** | 미인증 방문자 | 가입, 로그인, 비밀번호 재설정 요청만 가능 |
| **회원** | 인증된 일반 사용자 | 자신의 백로그 데이터 전체 CRUD, 게임 마스터 신규 등록 |
| **탈퇴 유예 회원** | 탈퇴 요청 후 30일 이내 | **인증은 통과하되 인가는 제한.** 복구 확인 화면만 접근 가능 |
| **관리자** | 단일 계정 | 무제한. 마스터 수정/병합, 전체 조회 |

### 4.1 권한 설계 원칙

- **AUTH-P1.** 관리자는 현재 권한 제약이 없다. 단, **모든 관리자 행위는 감사 로그로 기록**한다.
  - 근거: 권한 제약은 나중에 조일 수 있지만, 감사 로그는 소급 생성이 불가능하다.
  - 감사 로그는 **데이터 변경뿐 아니라 조회 행위도 기록**한다. "볼 수는 있되 본 기록이 남는다"가 개인정보 통제의 실질적 수단이다.
- **AUTH-P2.** 게임 마스터의 최초 등록은 회원이, 등록 이후 수정은 관리자만 할 수 있다.
  - 회원은 마음에 들지 않는 마스터 값을 **개인 오버라이드로 덮어** 사용한다.
- **AUTH-P3.** 비밀번호는 단방향 해시로 저장한다. 관리자도 원문을 볼 수 없다. (알고리즘 미정 — OI-03)

## 5. 도메인 모델 개요

```
Member ──1:N── BacklogEntry ──N:1── Game (마스터, 전체 공유)
  │                  │
  │                  ├──1:N── Playthrough (회차)
  │                  │            ├── Device          (실행 기기)
  │                  │            └── PlatformAccount (플레이 계정)
  │                  │
  │                  ├──1:N── Acquisition (취득: 방식 + 계정 + 금액 — 재구매·DLC로 복수 가능)
  │                  ├──N:M── Tag        (개인 태그)
  │                  ├──N:M── Genre      (개인 장르 — 태그와 동일 메커니즘)
  │                  └── CoverImage      (개인 소유)
  │
  ├──1:N── PlatformAccount ──N:1── Platform (마스터)
  ├──1:N── Subscription    (구독 이력)
  └──N:M── Device          (보유 기기 — 입력 기본값 용도)
```

### 5.1 엔티티 책임

| 엔티티 | 책임 | 소유 |
|---|---|---|
| `Game` | 게임의 객관적 사실 (이름, 개발사, 퍼블리셔, 장르, 출시일, 정가) | 전체 공유 |
| `BacklogEntry` | "나의 기록" 전체를 묶는 루트 | 개인 |
| `Playthrough` | 1회 플레이의 기간·상태·환경 | 개인 |
| `Acquisition` | 취득 방식·경로·금액 | 개인 |
| `Subscription` | 구독 서비스 가입 이력과 요금 | 개인 |
| `Platform` | 유통·계정 체계 마스터 | 전체 공유 |
| `PlatformAccount` | 회원이 보유한 플랫폼별 계정 | 개인 |
| `Device` | 실행 기기 마스터 | 전체 공유 |
| `Tag` | 개인 태그 (사전 메커니즘 — §6.7) | 개인 |
| `Genre` | 개인 장르 (태그와 동일한 사전 메커니즘 — §6.7) | 개인 |
| `CoverImage` | 커버 이미지 URL·메타데이터 | 개인 |

### 5.2 핵심 설계 결정 ①: 마스터 + 오버라이드

**결정**: 게임 마스터는 고정하고, 개인 수정값은 백로그 항목에 별도 저장한다.

**표시 규칙**: `표시값 = 개인 오버라이드 ?? 마스터 값` (오버라이드를 지우면 마스터 값이 다시 표시됨)

**대안 검토 기록**

| 대안 | 채택 | 사유 |
|---|---|---|
| 마스터 고정 + 개인 오버라이드 | **채택** | 데이터 중복 없음, 마스터 갱신 시 전체 반영 |
| 담을 때 마스터를 개인별로 복사 | 기각 | 회원 수만큼 데이터 복제, 학습 가치 낮음 |

**오버라이드 대상 필드**: 게임명, 개발사, 퍼블리셔, 출시일, 정가

> **장르는 오버라이드 필드가 아니다 (v1.3).** 개인 장르 사전(§6.7)으로 처리한다. 의미는 같은 `개인값 ?? 마스터값`이되, 문자열 컬럼이 아니라 사전 엔티티 구조다.

> **비용 인식**: 이 방식은 조회 시 `COALESCE(개인값, 마스터값)` 형태가 되어 인덱스가 동작하지 않는다. §7.2에서 비정규화로 해결한다.

### 5.3 핵심 설계 결정 ②: 플랫폼 / 계정 / 기기의 3축 분리

**결정**: 유통 체계(Platform), 계정(PlatformAccount), 실행 환경(Device)을 각각 분리한다.

| 축 | 예시 | 붙는 위치 |
|---|---|---|

> ### ⚠️ 운영 제약 — 메일 발송 불가로 인한 일시적 잠금 (v1.9)
>
> **자체 도메인이 없어 인증 메일을 보낼 수 없다.** 이 제약이 아래 넷을 잠근다.
>
> | 기능 | 지금 | 원래 |
> |---|---|---|
> | FR-AUTH-01 이메일 가입 | 허용 목록의 주소만 | 누구나 |
> | 비밀번호 **설정** (구글 전용 계정) | 불가 | 가능 |
> | FR-AUTH-05 재설정으로 비밀번호 **생성** | 불가 | 가능 |
> | FR-AUTH-08 구글 연결 해제 | **불가. 탈퇴만** | 비밀번호가 있으면 가능 |
>
> **왜** — Resend는 도메인 인증 전까지 계정 소유자에게만 보낸다. 유일한 우회로였던 SMTP 직접 발송은
> Render 무료 플랜이 2025-09부터 아웃바운드(25/465/587)를 막았다. 메일이 안 가면 계정은 미인증으로
> 남고 로그인이 영영 403이다(FR-AUTH-02) — **가입시키고 못 들어오게 하느니 가입을 거절하는 게 낫다.**
>
> **왜 구글은 되나** — 구글이 이메일 소유를 확인해 준다. 우리가 메일을 보낼 이유가 없다.
>
> **왜 해제까지 막나** — 이메일 가입과 비밀번호 설정이 둘 다 막힌 상태에서 연결까지 끊으면
> **로그인 수단이 하나도 안 남는다.** 되돌릴 방법이 없으므로 통째로 닫았다.
> 계정 정리는 탈퇴로 한다 — 30일 유예가 있어 되돌릴 수 있다 (FR-AUTH-09/10).
>
> **대가** — 구글 계정을 잃으면 이 서비스 계정도 잃는다. 원래 그 복구 경로(재설정으로 비밀번호 생성)는
> 어차피 메일이 배달되지 않아 실효가 없었고, 열어두면 비밀번호 설정 차단을 우회하는 구멍만 됐다.
>
> **가입 승인제(FR-ADM-06)와는 별개다.** 이건 "메일을 못 보내서" 막은 것이고,
> 승인제는 "무료 티어 용량을 지키려고" 막은 것이다. 도메인이 생겨도 승인제는 남는다.
>
> **원복 방법** — 도메인을 사서 Resend에 인증하고 `app.mail.from`을 그 주소로 바꾼 뒤,
> `app.signup.email-allowlist`를 비우고 `MemberService.changePassword`·`PasswordResetService.reset`·
> `Member.unlinkGoogle`의 차단을 되돌린다. 관련 테스트는 `SignupRestrictionTest`.

#### 상세 규칙

**FR-AUTH-02 이메일 인증**
- 인증 토큰: 랜덤 문자열, 만료 시각 보유, **1회용**(사용 즉시 폐기)
- 토큰은 **해싱하여 저장**한다. DB가 유출돼도 토큰을 사용할 수 없어야 한다
- 미인증 상태에서 재발송을 요청할 수 있다

**FR-AUTH-05 비밀번호 재설정**
- 토큰 구조는 FR-AUTH-02와 동일하다 (랜덤 / 만료 / 1회용 / 해싱 저장)
- **계정 존재 여부를 노출하지 않는다.** 가입 여부와 무관하게 동일한 응답을 반환한다
  - 근거: 응답이 다르면 가입자 이메일 목록을 열거할 수 있다
- 재설정 성공 시 기존 세션을 전부 무효화한다

**FR-AUTH-06~08 Google 계정 연동**

- **기존 계정에 연결하는 것은 로그인된 상태에서만 가능하다.**

| 방식 | 채택 | 사유 |
|---|---|---|
| 이메일 동일 시 자동 연결 | 기각 | 공격자가 타인 이메일로 선점 가입 시 계정 탈취 가능 |
| 별도 계정으로 취급 | 기각 | 데이터 분리로 사용성 저하 |
| 로그인 상태에서 수동 연결 | **채택** | 실무 표준, 학습 가치 |

- **BR-AUTH-01** (v1.9 강화): ~~비밀번호가 설정되지 않은 계정은~~ → **모든 계정이** 소셜 연결을
  해제할 수 없다. 근거는 같다(로그인 수단 소멸 방지)지만, 비밀번호를 새로 만드는 경로가 전부 막혀
  "비밀번호가 있으면 허용"이라는 예외가 성립하지 않는다. 위 운영 제약 참고

**FR-AUTH-12 Google 가입** (v1.6 신설 — Phase 3 I-6)

| ID | 요구사항 | 등급 |
|---|---|---|
| FR-AUTH-12 | 구글 계정으로 신규 가입할 수 있다 | SHOULD |

연결(FR-AUTH-06)과 **다른 기능이다.** 연결은 "이미 있는 내 계정에 로그인 수단을 하나 더 붙이는 것",
가입은 "계정 자체를 만드는 것"이다. 위 결정표의 기각 항목은 그대로 유효하다 —
여기서 여는 것은 **새 계정 생성**이지 기존 계정과의 자동 결합이 아니다.

| 상황 | 동작 |
|---|---|
| 이 `sub`로 연결된 회원이 있다 | 로그인 |
| 없고, 이메일도 미가입 | **가입** — 비밀번호 `null`인 소셜 전용 계정 |
| 없는데 **이메일이 이미 가입돼 있다** | **거부.** `409 EMAIL_ALREADY_REGISTERED` + "로그인 후 설정에서 연결" 안내 |
| 구글이 이메일을 안 준다 | 거부. 이메일 없이는 계정을 만들 수 없다 |

- **이메일 충돌 시 이어붙이지 않는 이유는 결정표 1행과 같다.** 이어붙이는 순간이 곧 탈취 시점이다
- 탈퇴 유예 중인 이메일도 여기서 걸린다 (BR-AUTH-02)
- 구글이 `email_verified: true`를 주면 **우리 인증 메일을 건너뛴다.** 소유 확인을 두 번 할 이유가 없다.
  `false`면 우리 인증 메일을 보내고, 인증 전에는 구글 로그인도 `403 EMAIL_NOT_VERIFIED`다 (FR-AUTH-02와 같은 규칙)
- 닉네임은 구글 `name` → 없으면 이메일 앞부분, 30자로 자른다
- ~~**소셜 전용 계정은 비밀번호 재설정 경로로 비밀번호를 만들 수 있다.**~~ **v1.9에서 막았다.**
  재설정 메일 자체가 배달되지 않아 실효가 없었고, 열어두면 비밀번호 설정 차단을 우회하는 구멍이 된다.
  재설정은 **잊은 비밀번호를 되찾는 경로지 새로 만드는 경로가 아니다** — 위 운영 제약 참고

**FR-AUTH-09~10 탈퇴 유예**
- 탈퇴 요청 시 `deletedAt`을 기록한다 (소프트 삭제)
- 유예 기간 30일. 경과 후 **스케줄 배치가 물리 삭제**한다
- 유예 중 로그인 시 **인증은 성공하되 인가를 제한**하여 복구 확인 화면으로 유도한다
- **BR-AUTH-02**: 이메일/아이디는 유예 기간 중 재사용할 수 없다 (유니크 제약 유지)

#### 마스터 필드

**v1.7에서 마스터의 성격이 바뀌었다** — "식별에 필요한 최소"에서 **"IGDB 미러"** 로.
상세 화면이 IGDB가 주는 것을 거의 그대로 보여주기로 하면서 필드가 11개에서 20개로 늘었다.

| 필드 | 출처 | 비고 |
|---|---|---|
| 원본 게임명 (영문) | IGDB `name` / 수동 | 오버라이드되어도 원본은 유지 |
| 개발사 (복수) | IGDB `involved_companies` (`developer = true`) / 수동 | |
| 퍼블리셔 (복수) | IGDB `involved_companies` (`publisher = true`) / 수동 | |
| 장르 (복수) | IGDB `genres` / 수동 | 참고값. 개인 장르가 없을 때의 표시·집계 폴백 (§6.7) |
| 출시일 | IGDB `first_release_date` — **전 플랫폼 중 가장 이른 날짜** | IGDB가 이미 최솟값으로 준다. 없으면 미정으로 보고 null |
| 정가 | **수동 입력** | IGDB는 가격을 안 준다. §8.1 참고 — **자리만 두고 화면에 출력하지 않는다** |
| 커버 이미지 ID | IGDB `cover.image_id` | 세로 박스아트. 개인 커버가 없을 때의 폴백 (§6.10) |
| **배너 이미지 ID** | IGDB `artworks[].image_id` | 가로 키아트. 상세 화면 상단용. **개인 배너는 두지 않는다** |
| **소개 (About)** | IGDB `summary` | 영문 원문 그대로. 번역·수정하지 않는다 |
| **스토리라인** | IGDB `storyline` | 〃 |
| **IGDB 평점** | IGDB `rating` | **유저 평점.** 0~100 |
| **IGDB 평점 표본 수** | IGDB `rating_count` | 표본이 수천 단위라 신뢰도 판단에 쓴다 |
| **출시 플랫폼 (복수)** | IGDB `platforms.abbreviation` | PS5·Switch·PC 같은 **하드웨어 기종** ⚠️ |
| **클리어 소요 — 메인** | IGDB `game_time_to_beats.hastily` (초 → 시간) | Main Story |
| **클리어 소요 — 메인+곁가지** | 〃 `normally` | Main + Extra |
| **클리어 소요 — 완주** | 〃 `completely` | Completionist |
| **클리어 소요 표본 수** | 〃 `count` | 10~70 수준. **퍼센트로 환산하지 않는다** |
| `source` | `IGDB` \| `MANUAL` | |
| `externalId` | IGDB 게임 ID | `MANUAL`인 경우 null |
| `lastSyncedAt` | 마지막 동기화 시각 | 재동기화 판단 기준 |

- **모든 필드는 null을 허용한다.** 정보가 없는 상태를 정상으로 취급한다
- **새로 늘어난 필드는 전부 오버라이드 대상이 아니다.** 표시값 규칙(§7.1)은 7개 그대로다

> ⚠️ **"출시 플랫폼"과 "플랫폼"은 다른 개념이다.**
> `Platform` 엔티티는 Steam·PSN·Nintendo 같은 **유통·계정 체계**이고(§2 용어),
> 여기 `releasePlatforms`는 PS5·Switch·PC 같은 **하드웨어 기종**이다.
> 값이 비슷해 보여도 소유 주체가 다르다 — 화면 라벨도 "출시 플랫폼" / "플랫폼 계정"으로 가른다.
> `Device`(내가 보유한 기기)와도 겹쳐 보이지만 엮지 않는다.

> **v1.7 개정 — 클리어 소요 시간을 3개로 쪼갠다**
> v1.6에서 `averagePlaytimeHours`(RAWG `playtime`, Steam 평균 플레이 시간)를
> `timeToBeatHours`(IGDB `normally`)로 바꿨는데, 상세 화면이 Main Story / Main+Extra /
> Completionist 세 축을 요구해 다시 쪼갠다. **같은 자리를 두 번 고친 셈이라 이력을 남긴다.**
> `normally`가 곧 "Main + Extra"이므로 v1.6의 값은 그 자리로 이어진다.

> **채택하지 않은 것**
> - **All Styles** — HowLongToBeat 고유 지표로 IGDB에 없다. 세 값의 평균으로 만들어 붙이면
>   출처가 다른 숫자에 HLTB 라벨을 다는 셈이라 **표시하지 않는다**
> - **Confidence(%)** — IGDB는 표본 수(`count`)만 준다. 퍼센트 환산 공식이 없으므로
>   **표본 수를 그대로 보여준다**
> - **평론가 평점(`aggregated_rating`)** — 유저 평점만 쓰기로 했다. 상세 화면의 "Critic Rating"
>   자리는 IGDB 유저 평점이 대신한다
> - **Game Modes / Themes / Perspectives / 플랫폼별 출시일** — IGDB가 전부 주지만 쓰지 않는다.
>   컬렉션이 4개 더 늘어나는 비용에 비해 화면 가치가 낮다

> **v1.6 개정 — 커버 이미지 필드를 마스터에 둔다**
> 기존: "커버 이미지 필드는 마스터에 두지 않는다". RAWG가 박스아트를 주지 않아서 내린 결정이었다.
> IGDB는 진짜 세로 박스아트를 주므로 마스터에 `coverImageId`를 둔다.
> **커버의 소유 모델(§6.10)은 바뀌지 않는다** — 개인 업로드가 여전히 우선이고,
> 마스터 커버는 그것이 없을 때의 폴백일 뿐이다.

**FR-GAME-04 수동 등록**

- **등록 이후 수정은 관리자만 가능하다** (AUTH-P2)
- 임포트 시 IGDB 매칭에 실패한 게임도 이 경로로 처리한다

**FR-GAME-05 재동기화**
- `lastSyncedAt` 기준 일정 기간 경과 시 재조회한다
- **개인 오버라이드는 재동기화의 영향을 받지 않는다**

#### 상세 규칙

**FR-BL-02 중복 방지**
- **DB 유니크 제약** `(member_id, game_id)`로 보장한다

- **되돌리기는 복원 "시도"다.** 무조건 성공하는 연산이 아니다
  - 스냅샷 상태가 현재의 검증 규칙(BR-PT-01~04 등)을 통과해야 커밋한다
  - 스냅샷이 참조하는 대상(기기, 계정 등)이 삭제되었으면 실패 처리한다

- Hibernate Envers는 채택하지 않는다 — 동작이 은폐되어 학습 목적에 맞지 않음

#### BR-PT-06 상태와 종료일 (v1.5 신설)

```
PLAYING              종료일 없어야 함        "지금 하는 중"과 종료일은 모순이다
PAUSED               종료일 있어도 없어도 됨   ← 여기만 자유
DROPPED | COMPLETED  종료일 있어야 함        끝났으면 언제 끝났는지가 있어야 한다
```

**개정 근거**: v1.4는 `PLAYING`·`PAUSED`를 묶어 "진행 중 = 종료일 없음"으로 정의했다. 그런데 실제 Obsidian 데이터에 **기간이 닫힌 `PAUSED`** 기록이 있었다.

```
포켓몬스터 소드 실드   2회차 2026.06.03 ~ 2026.06.11   Paused
루이지 맨션 3         1회차 2026.06.17 ~ 2026.06.19   Paused
```

"6/3~6/11 하다가 멈췄다"를 v1.4 모델로는 열린 기간으로밖에 못 담는데, 그러면 `lastPlayedOn`이 시작일(6/3)이 되어 **최근 플레이순 정렬이 8일 틀어진다.** 기본 정렬이 그것이므로(BR-QRY-01) 실제 오류다.

**BR-PT-03의 판정 기준을 상태가 아니라 종료일로 옮긴다.** 종료일을 적은 `PAUSED`는 시간을 점유하지 않으므로 새 회차를 막지 않는다. "회차를 닫는다"는 곧 **종료일을 적는 것**이며, 상태를 `DROPPED`/`COMPLETED`로 바꾸는 것이 아니다.

#### FR-PT-06 라벨의 용도 — DLC 처리

DLC는 별도 게임으로 관리하지 않고 **본편의 추가 회차로 흡수**한다.

```
1회차  2026-05-01 ~ 2026-06-20   (본편)
2회차  2026-10-05 ~ 2026-11-02   라벨: "DLC - 쿠파 왕국"
```

- DLC 구매 금액은 본편 백로그 항목에 **별도 취득 기록으로 남긴다** (v1.3 — 합산 방식 폐기). 취득 라벨로 구분한다. 예: `"DLC - 쿠파 왕국"`
- IGDB는 `dlcs[]`·`expansions[]`·`parent_game`으로 DLC 관계를 실제 목록으로 주지만, **호출하지 않는다.** DLC는 본편의 추가 회차로 기록하는 것이 이 서비스의 모델이다

#### 기기 선택 규칙

- **BR-PT-05** (v1.8 개정): 회차의 기기는 **회원이 등록한 기기 중에서** 고른다. 기기 마스터는 폐지했다.
  - 폐기된 규칙: "마스터 전체에서 선택. 보유 기기는 우선 표시일 뿐 제약이 아니다"
  - 폐기 근거: 마스터가 전역이라 **보유 기기를 추가해도 회차 선택지에 뜨지 않았다.** 회차는 마스터를,
    보유 기기는 별도 테이블을 가리켜 둘이 따로 놀았다. 같은 기종을 두 대 가져도 구분할 수 없었다
  - "친구 집에서 빌려 플레이한 기록"은 그 기기를 유형·라벨로 직접 추가하면 그대로 남길 수 있다

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-PLT-01 | 플랫폼별 내 계정을 등록·수정·삭제할 수 있다 | MUST |

| FR-PLT-04 | 플랫폼·에뮬레이터·입력 방식을 직접 등록·수정·삭제할 수 있다 | MUST |

> **선택지 소유권 개정 (v1.8)**
>
> 플랫폼·기기·에뮬레이터는 전역 마스터였고 입력 방식은 enum 4개였다. 넷 다 **회원 소유 테이블로 내렸다.**
>
> - 마스터는 모든 회원이 한 행을 공유해서, 오타 하나 고치려면 관리자 권한이 필요했다 (FR-ADM-04)
> - 기기는 마스터와 보유 기기가 따로 놀아 BR-PT-05의 문제를 낳았다 (§6.4)
> - 입력 방식은 enum이라 값을 늘리려면 배포가 필요했다
>
> 다섯 종(계정 포함) 전부 **소프트 삭제**다. 회차·취득이 참조하므로 행을 지우면 과거 기록이 빈다.
> 이름을 바꾸면 FK를 타고 그 항목을 쓴 모든 기록에 반영된다.
> 가입 시 기본 플랫폼·입력 방식이 회원 소유로 복사된다 (기기·에뮬은 개인 하드웨어라 비운다).
>
> 이 개정의 데이터 이행 마이그레이션(V2)은 **첫 실배포 전에 청산됐다** — 현재 스키마는
> 단일 베이스라인 `V1__init.sql`이 전부다 (`docs/db-baseline-v1.md`).

- `Platform`·`Device`·`Emulator`·`InputMethod`는 회원이 소유한다. 유니크는 각각
  `(member_id, name)` / `(member_id, label)` / `(member_id, name)` / `(member_id, name)`
- `Device`는 마스터를 참조하지 않는다. **유형**("Windows PC")과 **라벨**("메인 윈도우")을 직접 적고,
  라벨이 정체성이다 — 같은 기종을 여러 대 두려면 라벨로 구분한다. 메모는 마크다운
- `PlatformAccount`는 같은 회원의 `Platform`을 참조한다. 플랫폼을 지우면 딸린 계정도 함께 닫힌다
- 유니크 제약: `(member_id, platform_id, account_label)`
- 계정 라벨은 **표시용 별칭**이다. 실제 플랫폼 계정과 연동하지 않는다
- 계정 삭제는 **소프트 삭제**다. 회차·취득 기록이 참조하므로 보존한다 (§7.4)

#### 취득 방식 (enum)

`PURCHASED` | `SUBSCRIPTION` | `FREE` | `GIFT` | `BORROWED` | `DEMO` | `NOT_OWNED`

- `NOT_OWNED`는 **소유 여부만** 나타낸다. 지출 집계에서 빠지고 취득 목록에 방식으로 남는다
- **위시리스트는 취득 기록이 0건일 때다** (2026-08-26 개정). 예전엔 `NOT_OWNED`만 있으면
  위시리스트로 봤는데, 그러면 에뮬로 굴릴 롬을 챙겨둔 것처럼 **손에 닿는 게 분명한 것까지**
  위시리스트로 갔다. 위시리스트는 "아직 아무 기록도 없이 갖고 싶은 것"이어야 한다
- 실물 구매 등 계정이 없는 경우 `PlatformAccount`는 null이며 `Platform`만 기록할 수 있다

#### 취득 카디널리티 (v1.3)

- `Acquisition`은 **별도 엔티티**이며 `BacklogEntry`와 **1:N**이다 (임베디드 미채택 — §13 미결 해소)
- 근거 시나리오: 같은 게임을 Steam으로 샀다가 Switch판으로 **재구매**하는 경우. 백로그 항목은 `(member, game)`당 1개이므로 취득이 복수여야 담긴다
- DLC 구매도 별도 취득 행이다 (§6.4)
- 취득에 **라벨**(자유 문자열, nullable)을 둔다. 예: `"스위치판 재구매"`, `"DLC - 쿠파 왕국"`
- BR-ACQ-01의 "게임 구매 금액 합계"는 모든 취득 행의 합이다

#### 금액 표현

- `Money` 값 타입 (`@Embeddable`): `amount`(`BigDecimal`) + `currency`
- **통화는 ISO 4217 코드 문자열로 저장한다.** enum을 쓰지 않는다 — 나중에 통화를 늘릴 때 스키마 변경이 필요 없다
- 초기 지원 통화: KRW, USD, JPY
- **저장은 항상 입력한 원본 통화 기준**이다

#### 구독 (Subscription)

| 필드 | 비고 |
|---|---|
| 서비스명 | 예: Xbox Game Pass. **문자열로 저장한다** (OI-06 해소 — v1.4) |
| 시작일 / 종료일 | |
| 요금 | `Money` |
| 결제 주기 | 월 / 연 |

> **OI-06 결정 근거 (v1.4)**: 서비스명을 마스터 엔티티로 두지 않는다. 다른 엔티티가 참조하지 않고, 통계 축도 아니며(지출은 §6.6의 두 축으로만 집계), 자동완성이 필요하면 기존 구독 이력에서 `DISTINCT`로 뽑으면 충분하다. 엔티티화의 이득이 없다.

#### 지출 집계 원칙

- **BR-ACQ-01**: 구독료는 개별 게임에 배분하지 않는다. 총 지출은 두 축으로 분리해 집계한다.

```
총 지출 = 게임 구매 금액 합계 + 구독료 합계
```

대안 검토: 구독 기간 중 플레이한 게임 수로 나누는 방식은 배분 기준이 자의적이라 기각.

### 6.7 태그와 개인 장르 (TAG)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-TAG-01 | 백로그 항목에 개인 태그를 **하나** 붙일 수 있다 (v1.6) | MUST |
| FR-TAG-02 | 태그 이름을 변경하거나 삭제할 수 있다 | MUST |
| FR-TAG-03 | 태그로 필터링하여 조회할 수 있다 | MUST |
| FR-TAG-04 | 입력 시 기존 태그/장르를 자동완성으로 추천한다 | SHOULD |
| FR-TAG-05 | 개인 장르는 태그와 동일한 사전 메커니즘을 따른다 | MUST |

#### 항목당 태그는 하나다 (v1.6 개정 — 2026-08-26)

**바뀐 것**: `backlog_entry_tag` 조인 테이블을 폐기하고 `backlog_entry.tag_id`(nullable FK)로 옮겼다.

**근거** — 이 앱에서 태그는 설명용 메타데이터가 아니라 **묶는 장치**다. 디자인 요청서가
"태그는 카드에 안 넣는다, 사이드바와 폴더 뷰에서만 쓴다"고 못박은 것이 그 뜻이다.
묶는 게 목적이면 다중 소속은 같은 게임을 여러 그룹에 띄워 **이동용 목록의 스캔을 방해할 뿐**
얻는 게 없다. 서술용 다중값은 개인 장르가 이미 맡는다 — `장르 = 무엇인가` / `태그 = 내가 어디에 뒀나`.

**감수**: `명작`과 `운동`이 둘 다 참인 게임에서 하나를 골라야 한다. 정보가 준다는 것을 알고 택했다.

**시점 근거**: Neon이 비어 있는 동안 바꿨다. 데이터가 쌓인 뒤였다면 항목마다 어느 태그를
남길지 정하는 이행 작업이 붙는다.

#### 사전(Dictionary) 메커니즘 (v1.3)

태그와 개인 장르는 **IntelliJ 사전과 같은 방식**으로 동작한다.

- **등록 절차가 없다.** 항목에 적으면 목록에 생긴다
- **자동완성**: 다른 항목에서 입력할 때 기존 목록을 추천으로 보여준다
- **자동 소멸**: 어떤 백로그 항목에도 연결되지 않게 되면 목록에서 사라진다. **삭제 시점은 연결 해제 즉시다** (OI-13 해소 — v1.4)
  - **구현 (v1.5 개정)**: 사전 행을 지우지 않는다. **조회에서 연결이 1건 이상인 것만 반환**한다. 연결을 뗄 때는 연결 행만 삭제하고 사전 행은 그대로 둔다
  - 개정 근거: 기존 방식(COUNT → 0이면 DELETE)은 읽고-쓰기 사이에 경쟁 상태가 있었다. 두 요청이 동시에 마지막 연결을 떼면 둘 다 0을 보고 둘 다 지우려 든다. 조회에서 거르면 경쟁 대상 자체가 사라지고, **지연도 0이라 "즉시 사라진다"를 그대로 만족**한다
  - 부수 효과: 뗐던 태그를 다시 붙이면 **원래 행을 재사용**한다. 새 행을 만들지 않으므로 유니크 제약과 충돌하지 않는다
  - 감수: 연결이 0인 행이 테이블에 남는다. 조회에 안 잡히므로 기능상 무해하며, 정리가 필요해지면 그때 청소 쿼리를 둔다 (배치 지연이 문제되지 않는다 — 어차피 보이지 않는다)
  - **`orphanRemoval`이나 `CascadeType.REMOVE`로는 불가능하다.** 하나의 `Tag`를 여러 `BacklogEntry`가 공유하므로 부모가 하나로 특정되지 않는다 (항목당 태그가 하나가 된 v1.6에서도 이 공유는 그대로다)
  - 배치 **정리**를 소멸 수단으로 택하지 않은 이유: 자동완성 목록에 "쓰지 않는 태그"가 배치 주기만큼 남아 보이는 것이 사전 메커니즘의 취지에 어긋난다. 위 조회 필터는 이 문제가 없다
- 검색·필터의 옵션 목록은 이 사전이 기준이다
- UI에서 태그는 폴더처럼 표시할 수 있다 (데이터 구조는 평면, 표현만 폴더). 항목당 하나라 **한 게임은 한 폴더에만 있다**

#### 태그 vs 장르

메커니즘은 같고 **용도(통계 축)가 다르다.**

| 구분 | 장르 | 태그 |
|---|---|---|
| 용도 | 게임 분류, 장르별 통계(FR-STAT-01) | 자유 분류 — 폴더처럼 묶는다 |
| 개수 | 항목당 여러 개 | **항목당 최대 1개** (v1.6) |
| 마스터와의 관계 | 개인 장르가 1개 이상이면 개인 장르를, 없으면 마스터(IGDB) 장르를 표시·집계에 사용 | 마스터 없음 |

- 태그·장르 모두 **회원 소유**다. 다른 회원과 공유하지 않는다
- 유니크 제약: `(member_id, name)` — 태그·장르 각각
- 계층 구조(폴더 트리)는 두지 않는다. 평면으로 시작한다
- 마스터(IGDB) 장르는 참고값으로 유지되며, 개인 사전과 섞이지 않는다
- 용도 예시(태그): `"친구와 함께한 게임"`, `"명작"` / (장르): `"세미 오픈 월드"`, `"플랫포머"`

### 6.8 조회 (QRY)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-QRY-01 | 백로그 목록을 페이징하여 조회한다 | MUST |
| FR-QRY-02 | 게임명으로 검색한다 | MUST |
| FR-QRY-03 | 상태·태그·장르·기기·플랫폼 계정으로 필터링한다 | MUST |
| FR-QRY-04 | 이름·평점·출시일·최근 플레이순으로 정렬한다 | MUST |
| FR-QRY-05 | 백로그 항목 상세를 조회한다 | MUST |

#### 상세 규칙

- **검색/정렬 대상은 비정규화 컬럼이다** (§7.2). 오버라이드와 마스터를 매번 합성하지 않는다
- **정렬 기본값**: 최근 플레이순
- **BR-QRY-01**: 동점 시 2차 정렬 기준은 최근 플레이순으로 한다
  - 2차 기준을 정하지 않으면 정렬 결과가 매 요청마다 달라져 페이징이 깨진다
- 응답은 **반드시 DTO로 변환**한다. 엔티티를 직접 반환하지 않는다
- 장르·태그 필터의 옵션 목록은 **개인 사전**(§6.7) 기준이다

#### 우선순위와 감수 사항

- **본 기능군의 우선순위는 `필터링·정렬 > 검색`이다.** 게임 수가 늘어도 태그·상태·장르로 좁히는 쪽이 실사용 빈도가 높다
- **한글 검색 범위**
  - 검색 대상은 `displayName`(개인 오버라이드 이름 ?? 마스터 원본명)이다. **이미 담은 게임은 한글로 적어두면 한글로 검색된다**
  - 반면 **아직 담지 않은 게임을 IGDB에서 찾을 때는 영문으로 검색해야 한다.** IGDB에 `korea` 리전이 존재하지만 로컬라이제이션 데이터가 0건이라(실측, `docs/igdb-survey.md`) 한글 제목을 얻을 수 없다. **해결하지 않고 감수하는 제약**이다 (별칭 필드를 두지 않기로 한 결정과 연결됨 — §3.2)

#### 성능 요구 (N+1 대응)

목록 조회는 `Game`, `Playthrough`, `Tag` 등 다수의 연관을 함께 필요로 하므로 N+1이 발생하기 쉽다.

- `~ToOne` 연관 → **fetch join**
- 컬렉션(`~ToMany`) → **지연 로딩 + batch size**
  - 컬렉션 fetch join은 행이 증폭되고, **페이징이 불가능해진다** (전체를 메모리에서 자르므로 OOM 위험)
- 모든 `~ToOne` 연관은 `FetchType.LAZY`를 **명시**한다

### 6.10 커버 이미지 (MED)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-MED-01 | 백로그 항목에 커버 이미지를 업로드할 수 있다 | MUST |
| FR-MED-02 | 커버가 없으면 마스터 커버 → 기본 이미지 순으로 폴백한다 | MUST |
| FR-MED-03 | 커버를 교체·삭제할 수 있다 | MUST |
| FR-MED-04 | 스크린샷/영상을 첨부할 수 있다 | COULD |

#### 상세 규칙

- **업로드한 커버는 개인 소유다.** 다른 회원과 공유하지 않는다
- **표시 우선순위는 `개인 업로드 ?? 마스터 커버 ?? 기본 이미지`다** (FR-MED-02)
  - 마스터 커버는 IGDB `cover.image_id`로, `//images.igdb.com/igdb/image/upload/{size}/{image_id}.jpg` 형태로 조합한다
  - 크기는 자리마다 다르게 쓴다 (전부 200 응답 실측):

    | 자리 | size | 실측 | 용량 |
    |---|---|---|---|
    | 검색 결과 행·사이드바 등 좁은 자리 | `t_micro` | 40×40 | 0.9KB |
    | 목록 카드 | `t_cover_small` | 90×120 | 3.7KB |
    | 상세 | `t_cover_big_2x` | 528×704 | 60KB |

  - **`t_micro`·`t_thumb`은 정사각 크롭이다.** 세로 박스아트가 잘리므로 **아이콘으로 읽히는 자리에만** 쓴다.
    비율이 중요한 자리(카드·상세)는 `t_cover_*`를 쓴다
  - **배너(`bannerImageId`)는 가로 이미지라 크기 프리셋이 다르다** (전부 200 실측):

    | 자리 | size | 실측 |
    |---|---|---|
    | 상세 상단 배너 | `t_screenshot_huge` | 1280×720 |
    | 고해상도 | `t_1080p` | 1726×1080 |

  - ⚠️ **size 이름은 리사이즈 프리셋일 뿐 비율을 정하지 않는다.** 비율은 원본이 결정한다 —
    가로 아트워크에 `t_cover_big`을 쓰면 264×352가 아니라 **264×165**가 나온다
  - **파일을 우리 스토리지로 복사하지 않는다.** IGDB CDN URL을 그대로 참조한다 — 마스터 커버는 우리 소유가 아니다
- v1.5까지는 "RAWG의 이미지는 스크린샷/키아트라 쓰지 않는다"였다. IGDB는 진짜 박스아트를 주므로 폴백으로 채택한다
- **파일은 오브젝트 스토리지에 저장하고 DB에는 URL과 메타데이터만 저장한다**
  - 근거: 무료 티어 DB 용량(0.5GB 수준)으로 이미지를 감당할 수 없다
- **업로드 방식: presigned URL — 2단계다**
  1. `POST /api/backlog/{id}/cover/upload-url` → 서명된 URL + `storageKey` + `contentType`
  2. 브라우저가 그 URL로 직접 `PUT` (**응답의 `contentType`을 그대로 헤더에 써야 한다** — 서명 대상이라 다르면 스토리지가 403)
  3. `PUT /api/backlog/{id}/cover` `{ storageKey }` → 확정
  - 서버는 업로드 성공 여부를 모른다. 그래서 확정 단계가 따로 있고, 클라이언트의 말을 믿지 않고 실물을 확인한다
  - 근거: 서버 경유 시 메모리 압박(무료 티어 512MB)과 요청 점유 시간 증가
  - 확정되지 않은 업로드는 고아 파일로 남는다 → **버킷 라이프사이클 규칙으로 자동 삭제** (Phase 9에서 설정)

- **검증은 세 겹이다.** presigned 방식에서는 서버가 파일 바이트를 한 번도 안 거치기 때문이다

  | 단계 | 검사 | 근거 |
  |---|---|---|
  | 발급 시 | 확장자·MIME 화이트리스트(jpg/png/webp), 선언 크기 상한(기본 5MB) | 클라이언트 주장 |
  | 서명 | `Content-Type`·`Content-Length`를 **서명에 포함** | 다른 값으로 올리면 **스토리지가 거부**한다 |
  | 확정 시 | 실제 크기 재확인 + **앞 12바이트 매직 넘버 검사** | 확장자만 이미지인 위장 파일 차단 |

  - 매직 넘버를 아는 형식만 허용한다. `gif`·`svg`를 뺀 이유 — 검사할 수 없는 형식을 열면 세 번째 방어가 무의미해지고, svg는 스크립트를 품을 수 있다
  - **`storageKey`는 `covers/{memberId}/{entryId}/{uuid}.{ext}`다.** 확정 시 이 prefix를 검사해 **남의 경로 파일을 자기 커버로 붙이는 것을 막는다.** 회원 탈퇴 시 prefix 하나로 통삭제도 된다

- **정리**: 커버 교체·삭제 시 기존 파일을 스토리지에서 제거한다
  - **순서는 `DB 커밋 → 스토리지 삭제`다.** 뒤집으면 파일은 없는데 DB엔 남는 상태가 생긴다.
    이 순서에서 최악은 고아 파일이 남는 것뿐이고, 라이프사이클 규칙이 정리한다
  - 스토리지 삭제 실패는 사용자에게 실패로 알리지 않는다 — 이미 커밋된 삭제가 실패한 것처럼 보인다

#### 트랜잭션 전략

- **BR-IMP-02**: 행(파일) 단위로 트랜잭션을 분리한다. 전체를 하나로 묶지 않는다
  - 파일 전체를 한 트랜잭션으로 묶으면 1건 실패 시 전부 롤백된다

- 롤백 기능은 제공하지 않는다

#### 감수 사항 — `inputMethod` 유실 (v1.5)

실데이터의 `inputMethod`는 **리스트**다.

```yaml

  - keyboard & mouse
  - controller (XBox)
```

`Playthrough.inputMethod`는 **단일 enum**으로 유지하기로 결정했다. 한 회차에서 입력 방식을 여러 개 쓴 기록은 **하나만 남고 나머지는 유실된다.**

- 근거: 입력 방식은 통계 축도 필터 조건도 아니다(FR-PT-05는 SHOULD). 리스트로 만들면 조인 테이블이 하나 더 생기는데 그만한 값어치가 없다
- 임포트 시 어느 것을 남길지는 Phase 7에서 정한다 (첫 항목 또는 대표값)

>

>

>

## 7. 데이터 규칙

### 7.1 표시값 규칙 (v1.7에서 "오버라이드 규칙"에서 개칭)

```
표시값 = COALESCE(개인 값, 마스터 값)
```

**개인 값이 마스터를 덮는 자리는 7개다.** `Game`은 전 회원 공용이라 **절대 수정되지 않고**,
개인 값은 `BacklogEntry` 쪽에 따로 쌓여 읽을 때 합성된다.

| 표시 항목 | 개인 값이 사는 곳 | 폴백 판정 |
|---|---|---|
| 이름 | `BacklogEntry.nameOverride` | `?? 마스터` → `displayName` 비정규화 |
| 개발사 | `BacklogEntry.developerOverrides` | `isEmpty()` |
| 퍼블리셔 | `BacklogEntry.publisherOverrides` | `isEmpty()` |
| 출시일 | `BacklogEntry.releasedOnOverride` | `?? 마스터` → `releasedOnResolved` 비정규화 |
| 정가 | `BacklogEntry.listPriceOverride` | `?? 마스터` |
| **장르** | `BacklogEntryGenre` 조인 테이블 | 1개라도 있으면 개인 것만 (§6.7) |
| **태그** | `backlog_entry.tag_id` (v1.6) | 마스터 개념이 없다. null이면 "태그 없음" |
| **커버** | `CoverImage` 별도 엔티티 | 있으면 개인 것 (§6.10) |

> **왜 셋의 저장 방식이 다른가** — 데이터 모양 때문이지 자의적인 구분이 아니다.
> 앞의 5개는 스칼라·단순 리스트라 `BacklogEntry`의 컬럼으로 충분하다.
> **장르**는 개인 *사전*(`Genre`)을 여러 항목이 공유해야 이름 변경·자동 소멸이 성립하므로 조인 테이블이다.
> **커버**는 파일 메타(`storageKey`·`contentType`·`sizeBytes`)라 값 하나가 아니고, 삭제 시 스토리지 정리가 딸린다.
>
> 다만 **부르는 이름은 하나로 통일한다.** v1.6까지 앞의 5개만 "오버라이드"라 불러
> 장르·커버가 같은 규칙임이 드러나지 않았다.

- 개인 값을 null(또는 빈 컬렉션)로 지우면 마스터 값이 다시 표시된다
- 마스터 재동기화는 개인 값에 영향을 주지 않는다
- **응답에서는 7개가 전부 `resolved` 안에 모인다.** 커버도 예외가 아니다 —
  `resolved.cover.source`로 어느 쪽이 이겼는지 서버가 알려주고, **크기 선택만 화면 몫**이다
  (마스터 커버는 자리마다 크기가 달라야 해서 서버가 URL을 확정하면 안 된다, §6.10)
- **v1.7에서 늘어난 마스터 필드(배너·소개·평점·출시 플랫폼·클리어 소요)는 전부 표시값 규칙 밖이다.**
  덮을 수단이 없고, 덮을 이유도 없다 — 내 평가는 `rating`, 내 시간은 `playTimeHours`가 따로 있다

### 7.2 비정규화 컬럼 (의도적 정규화 위반)

`BacklogEntry`는 조회 성능을 위해 파생값을 컬럼으로 보관한다.

| 컬럼 | 파생 원천 | 갱신 시점 |
|---|---|---|
| `displayName` | 이름 오버라이드 ?? 마스터 원본명 | 오버라이드 변경 시 |
| `status` | 취득 방식 + 최신 회차 상태 (§7.6) | 회차/취득 변경 시 |
| `lastPlayedOn` | 최신 회차의 종료일(또는 시작일) | 회차 변경 시 |
| **`lastPlaythrough`** (v1.5 신설) | 최신 회차 자체에 대한 참조 | 회차 변경 시 |

**근거**: 매 조회마다 `COALESCE(...)`나 서브쿼리로 계산하면 인덱스가 동작하지 않고, 필터·정렬·페이징 성능이 무너진다. 정규화를 의도적으로 깨는 대신 **갱신 책임을 서비스 계층이 진다.**

**`lastPlaythrough` 추가 근거 (v1.5)**: 목록 화면 카드가 **마지막 회차의 번호·기간·기기**를 표시한다. 매번 회차를 뒤지면 항목 수만큼 쿼리가 나가는데, 컬렉션은 fetch join 시 페이징이 깨지므로(§6.8) 우회가 어렵다. `~ToOne` 참조로 두면 **join fetch가 가능하고 페이징도 살아남는다.**

- 갱신 경로가 `syncDerivedState()` 한 곳뿐이라 유지 비용은 `lastPlayedOn`과 동일하다 (같은 자리에서 이미 최신 회차를 계산하고 있다)
- `lastPlayedOn`은 중복처럼 보이지만 **정렬 인덱스가 그 컬럼**이므로 함께 유지한다
- `backlog_entry ↔ playthrough` 순환 FK가 생긴다. 컬럼이 nullable이므로 Hibernate가 INSERT → UPDATE 순으로 처리하며, 삭제 시에도 UPDATE(참조 이동)가 DELETE보다 먼저 나간다

### 7.3 유니크 제약

| 대상 | 제약 | 목적 |
|---|---|---|
| `BacklogEntry` | `(member_id, game_id)` | 같은 게임 중복 담기 방지 |
| `Tag` | `(member_id, name)` | 태그 이름 중복 방지 |
| `Genre` | `(member_id, name)` | 개인 장르 이름 중복 방지 |
| `PlatformAccount` | `(member_id, platform_id, account_label)` | 계정 중복 등록 방지 |
| `Game` | `(source, external_id)` | 같은 IGDB 게임의 마스터 중복 등록 방지 |
| `Member` | `email` | 계정 중복 및 재사용 방지 |

> PK(id)는 행을 구분할 뿐 중복을 막지 않는다. **중복 방지의 최종 방어선은 DB 유니크 제약이다.** 애플리케이션 검증은 사용자 친화적 메시지를 위한 보조 수단이다.
>
> **소프트 삭제와의 충돌 (v1.3)**: 소프트 삭제된 행도 물리적으로 존재하므로 유니크 검사에 걸린다. 같은 값을 다시 만들면 유니크 위반이 난다. §7.4의 삭제 정책(되살리기 + 물리 삭제 혼합)이 이 충돌의 해소 방안이다.

### 7.4 삭제 정책 (v1.3 전면 개정)

> **v1.2의 "전 엔티티 소프트 삭제"를 폐기한다.** 두 가지 문제 때문이다.
> 1. **유니크 제약과 충돌**: 삭제된 행이 물리적으로 남아, 같은 값을 다시 만들면 유니크 위반이 난다. 예: 게임 삭제 후 재추가 → 409, 태그 `"명작"` 삭제 후 재생성 → 409
> 2. **마스터에 무의미**: `Game`을 소프트 삭제하면 전체 회원의 백로그 항목이 가리키는 대상이 숨겨져 깨진다. 마스터의 정리는 소프트 삭제가 아니라 병합(FR-ADM-02)의 몫이다

**엔티티별 삭제 방식**

| 엔티티 | 방식 | 근거 |
|---|---|---|
| `Member` | 소프트 → 유예 만료 시 배치 물리 삭제 | 탈퇴 유예(FR-AUTH-09). 유예 중 이메일 재사용 불가는 의도된 동작(BR-AUTH-02) |
| `BacklogEntry` | 소프트 + **되살리기(revive)** | 아래 되살리기 규칙 참조 |
| `PlatformAccount` | 소프트 + 되살리기 | 회차·취득이 참조하므로 보존(§6.5). 동일 라벨 재등록 시 되살리기 |
| `Tag` / `Genre` | **물리** | 미사용 시 자동 소멸이 스펙 자체(§6.7). 유니크 충돌 원천 차단. 태그 삭제는 `backlog_entry.tag_id`를 먼저 null로 밀고 지운다 |
| `Playthrough` / `Acquisition` / `Subscription` | **물리** | 부모(항목/회원)가 소프트 삭제되면 함께 숨겨지므로 자체 `deletedAt` 불필요. 개별 삭제 이력은 스냅샷(§7.5)이 담당 — 단, `Acquisition`·`Subscription`은 스냅샷 대상이 아니므로 이력 없이 삭제됨을 감수한다 |
| `Game` / `Platform` / `Device` (마스터) | **삭제 없음** | 정리는 관리자 병합·마스터 관리(FR-ADM-02/04) |
| `CoverImage` | 물리 (스토리지 파일 포함) | §6.10 정리 규칙 |
| 스냅샷 / 감사 로그 | **삭제 없음** | 지워지지 않는 것이 존재 이유인 테이블 |

**되살리기(revive) 규칙 — `BacklogEntry`**

```
재추가 요청
 ├─ 살아있는 행 존재   → 409 (FR-BL-02)
 ├─ 삭제된 행 존재     → "이전 기록을 복원할까요?" 확인 → deletedAt = null
 │                       기존 평점·회차·취득 기록이 그대로 돌아온다
 └─ 없음               → 신규 INSERT
```

- 되살리기 시 백지로 밀지 않고 **기존 데이터를 복원**한다 (제품 결정)
- 단순 INSERT가 3단계 분기가 되는 비용을 감수한다 — 이것이 소프트 삭제의 실제 가격이다

**소프트 삭제 대상 엔티티의 공통 규칙**

- `deletedAt` 컬럼을 두고, 조회 시 `deletedAt IS NULL` 조건이 항상 적용되어야 한다
- **위험**: 조회 한 곳에서 조건을 빠뜨리면 삭제된 데이터가 노출된다. 엔티티 레벨 자동 적용(`@SQLRestriction`)을 검토하되, 조건이 코드에 드러나지 않는 부작용을 인지한다. 특히 **되살리기 경로는 삭제된 행을 조회해야 하므로** `@SQLRestriction` 사용 시 네이티브 쿼리 등 우회가 필요하다

**부분 유니크 인덱스는 채택하지 않는다**

PostgreSQL의 `WHERE deleted_at IS NULL` 부분 인덱스가 정석 해법이지만, H2가 미지원이라 개발/운영 DB의 제약이 갈라진다. Flyway 전환(Phase 9) 시점에 재검토한다.

### 7.5 변경 이력 (스냅샷 방식 — v1.3)

- 대상: `BacklogEntry`, `Playthrough` **한정**
- 기록 항목: 대상 타입, 대상 ID, **스냅샷 JSON(엔티티 상태 전체)**, 변경자, 변경 시각
- 직렬화 범위: 엔티티 자신의 필드만. 연관은 **ID만** 저장한다 (객체 그래프를 통째로 직렬화하지 않는다)
- 복원 규칙은 FR-BL-09 참조 — 검증 통과 시에만 커밋, 참조 소멸 시 실패, 복원 후 비정규화 재계산
- 관리자 행위에 대한 감사 로그는 별도다 (§6.12)

### 7.6 상태 파생 규칙

| 조건 | `status` |
|---|---|
| 회차 없음 + 취득 **0건** | `WISHLIST` |
| 회차 없음 + 취득 1건 이상 (`NOT_OWNED` 포함) | `BACKLOG` |
| 회차 없음 + 그 외 취득 | `BACKLOG` (쌓아둠) |
| 진행 중 회차 존재 | `PLAYING` |
| 최신 회차가 `PAUSED` | `PAUSED` |
| 최신 회차가 `DROPPED` | `DROPPED` |
| 최신 회차가 `COMPLETED` | `COMPLETED` |

계산 가능한 값이지만 §7.2에 따라 컬럼으로 저장한다.

**"최신 회차"의 정의 (v1.3)**: 회차 번호가 아니라 **날짜 기준** — `COALESCE(종료일, 시작일)`이 가장 늦은 회차.

- 근거: 과거 플레이를 뒤늦게 입력해도(특히 Obsidian 임포트) 상태가 과거 회차에 끌려가지 않는다. 회차 번호 기준이면 "2026년에 완료한 게임에 2025년 중단 회차를 나중에 추가"하는 순간 상태가 `DROPPED`로 뒤집힌다
- 진행 중 회차(종료일 null)가 있으면 위 표에 따라 어차피 `PLAYING`이 우선한다

### 7.7 금액과 통화

- 저장: 원본 통화 + 금액 (`Money` 값 타입)
- 통화는 **ISO 4217 코드 문자열**로 저장한다 (enum 미사용 — 확장성)
- 표시: 초기에는 원본 통화 그대로 표시한다. 환율 변환은 후속 단계에서 도입한다

**환율 적용 원칙 (도입 시)**

| 대상 | 처리 |
|---|---|
| 정가 | 실시간 환율로 변환 가능 (현 시점 기준 참고값) |
| 구매가 | **실시간 환율 변환 금지.** 구매 시점 환율을 스냅샷으로 저장 |

근거: 과거 구매액을 현재 환율로 변환하면 실제 지출이 왜곡된다.

- 환율은 **1일 1회만 조회하여 캐시**한다 (`@Scheduled` 배치)

## 8. 외부 연동

### 8.1 IGDB (Internet Game Database)

| 항목 | 내용 |
|---|---|
| 용도 | 게임 검색 및 마스터 정보 수집 |
| 인증 | **Twitch OAuth2 client_credentials** — client id + secret으로 토큰 발급, 약 64일 만료 |
| 호출 | `POST https://api.igdb.com/v4/{endpoint}`, 본문은 **APIcalypse** 쿼리 |
| 호출 제한 | **초당 4회 / 동시 8건** (초과 시 429) |
| 라이선스 조건 | Twitch Developer Services Agreement. 비상업 무료. **출처 표기 의무 조항 없음** |
| 제공하지 않는 것 | 가격, 한국어 데이터 |
| 브라우저 직접 호출 | **CORS 차단** — 백엔드 경유 필수 |

**선정 근거 (v1.6 개정)**: v1.5까지는 RAWG를 썼다. 인증이 API 키 하나로 끝나고,
커버·DLC를 안 쓰기로 해서 IGDB의 장점이 사라졌다는 판단이었다.

**바꾼 이유는 데이터가 아니라 조달이다.** RAWG는 API도 데이터도 살아있지만
**가입·로그인 폼이 깨져 키를 새로 발급받을 수 없다**(2026-08 확인). 가진 키가 만료되면 복구 수단이 없다.
프론트엔드가 2024년에 폐쇄된 `cdn.polyfill.io`를 아직 로드하는 방치 상태다.

옮기면서 v1.5의 전제 두 개가 뒤집혔다 — IGDB는 **진짜 세로 박스아트**를 주고(§6.10 폴백으로 채택),
**지역별 출시일**도 준다(당장은 안 씀). 조사 실측은 `docs/igdb-survey.md`.

**한도 관리**: 온디맨드 캐시로 같은 게임은 1회만 호출된다. 개인 사용 패턴(검색 1·담기 1)은 초당 4회에 걸리지 않는다.
**단, Phase 7 임포트에서 파일 수십~수백 개를 매칭할 때는 반드시 걸린다** — 스로틀링·백오프는 M-3에서 다룬다.

**출처 표기**: RAWG와 달리 의무 조항이 없다. v1.5의 "초기부터 템플릿에 포함" 지시는 폐기하고,
대시보드 푸터에 남아 있는 RAWG 표기는 제거한다.

**실시간 가격은 범위 밖이다 (v1.7).** IGDB는 가격을 주지 않는다.
스토어별 시세·할인을 보려면 IsThereAnyDeal(ITAD) 같은 **세 번째 외부 의존**을 붙여야 하는데,
가격은 계속 변해서 온디맨드 캐시(§6.2) 전략이 통하지 않고 별도 갱신 주기가 필요하다.
정가는 수동 입력 자리만 두고 화면에 출력하지 않으며, 실제 지불액은 취득 기록(§6.6)이 갖는다.
필요해지면 `GameCatalogClient`처럼 포트를 하나 더 뽑는다.

### 9.1 성능

| ID | 요구사항 |

| NFR-P4 | 필터·정렬 대상 컬럼에 인덱스를 설계한다 |

### 9.2 보안

| ID | 요구사항 |
|---|---|
| NFR-S1 | 비밀번호는 단방향 해시로 저장한다. **BCrypt** (OI-03 해소, Phase 3 I-2) |
| NFR-S2 | 인증/재설정 토큰은 해싱하여 저장하고 1회용으로 폐기한다 |
| NFR-S3 | 계정 존재 여부를 응답으로 노출하지 않는다 |
| NFR-S4 | 외부 API 키는 환경변수로 관리하며 저장소에 커밋하지 않는다 |
| NFR-S5 | 업로드 파일의 확장자·MIME·용량을 검증한다 |
| NFR-S6 | 모든 입력값을 서버에서 재검증한다 |
| NFR-S7 | 타 회원의 데이터에 접근할 수 없다 (소유권 검증) |
| NFR-S8 | 관리자 행위는 조회를 포함해 감사 로그로 기록한다 |
| NFR-S9 | 인증·재설정 메일 재발송에 최소 간격 스로틀을 둔다 (v1.3 — 발송 한도 소진·스팸 악용 방지) |

> **NFR-S1 참고**: Spring Security의 `DelegatingPasswordEncoder`는 저장된 해시에 `{bcrypt}`, `{argon2}` 같은 접두어를 붙여 알고리즘을 식별한다. 따라서 나중에 알고리즘을 교체해도 기존 비밀번호를 폐기할 필요가 없다.

### 9.3 아키텍처

```
Controller   HTTP만 안다. DTO ↔ 서비스 호출
Service      트랜잭션 경계. 비즈니스 흐름 조율
Repository   JPA 직접 사용
Domain       비즈니스 규칙이 사는 곳
```

| ID | 요구사항 |
|---|---|
| NFR-A1 | 서비스 계층은 HTTP를 알지 못한다 |
| NFR-A2 | 의존성은 생성자 주입으로 받는다 |
| NFR-A3 | 엔티티를 API 응답으로 노출하지 않는다. DTO 변환은 트랜잭션 안에서 완료한다 |
| NFR-A4 | 규칙은 엔티티 안에 둔다 (도메인 모델 패턴). 서비스는 순서만 조율한다 |
| NFR-A5 | `@Transactional`은 클래스 레벨 `readOnly = true` + 쓰기 메서드에 개별 선언 |

### 9.4 운영

| ID | 요구사항 |
|---|---|
| NFR-O1 | 개발 전 기간 SQL 로그를 활성화한다 |
| NFR-O2 | 엔티티 안정화 후 Flyway를 도입하고 `ddl-auto: validate`로 전환한다 |
| NFR-O3 | **세션은 DB에 저장한다 (Spring Session + JDBC).** |

**NFR-O2 Flyway 도입 시점**
엔티티를 자주 수정하는 초기에는 `ddl-auto: create`가 훨씬 빠르다. **엔티티가 안정되고 배포가 임박한 시점에 전환한다.** Flyway는 DB 스키마 변경 이력을 SQL 파일로 관리하는 도구이며, `validate`는 하이버네이트가 스키마를 변경하지 않고 엔티티와의 일치 여부만 검사하게 한다.

**NFR-O3 세션 저장소**
Render 무료 티어는 인스턴스가 자주 재시작되어 **메모리 세션이 유실된다.** 재시작 시 전원 로그아웃되므로 Neon(PostgreSQL)에 세션을 저장하는 것이 사실상 필수다. Phase 9에서 적용한다.

| 리포지토리 구조 | 모노레포 — `docs/`, `backend/`, `frontend/`(Phase 8) |

#### 현재 의존성

`spring-boot-starter-webmvc`, `spring-boot-starter-data-jpa`, `spring-boot-starter-validation`, `spring-boot-h2console`, `lombok`, `h2`(runtimeOnly), 모듈별 테스트 스타터(`-data-jpa-test`, `-validation-test`, `-webmvc-test`), `p6spy-spring-boot-starter`

추가 예정: Spring Security(Phase 3), `spring-boot-starter-restclient`(Phase 4), QueryDSL(Phase 6 / L-1 — Hibernate 7 호환 버전 확인 필요, 커뮤니티 포크 `io.github.openfeign.querydsl` 검토), Flyway(Phase 9)

#### 데이터 접근 규약 (v1.4 추가)

Spring Data JPA를 쓰되 `JpaRepository`를 직접 상속하지 않는다.

```
BaseRepository<T, ID>          findById · findAll · delete · persist  (save() 없음)
    └─ BaseRepositoryImpl      SimpleJpaRepository 상속 + persist 구현
         MemberRepository / GameRepository / BacklogEntryRepository
```

- **근거**: `SimpleJpaRepository.save()`는 내부가 `if (새 엔티티) persist else merge`다. 준영속 엔티티에 `save()`를 부르면 조용히 `merge()`가 돌아 §설계 원칙(변경 감지 우선, `merge()` 금지)을 어긴다. 인터페이스에서 `save()`를 빼면 **컴파일 단계에서** 막힌다
- 신규 저장은 `persist()`, 수정은 **변경 감지**, 벌크는 `@Modifying` + `@Query`
- `@EnableJpaRepositories(basePackages = "com.milobeene.starlog", repositoryBaseClass = BaseRepositoryImpl.class)` — 이 애노테이션을 직접 달면 부트 자동 설정이 꺼지므로 `basePackages`를 반드시 명시한다

#### Spring Boot 4 주의사항 (v1.4 추가)

**참고 강의(JPA 활용편)는 Spring Boot 3.x 기준이므로 아래가 다르다.**

| 3.x | 4.x |
|---|---|
| `spring-boot-starter-web` | **`spring-boot-starter-webmvc`** |
| `spring-boot-starter-test` 하나 | **스타터마다 대응하는 `-test` 짝**을 따로 추가 |
| `h2` 의존성만으로 콘솔 동작 | **`spring-boot-h2console`** 별도 필요 |
| `org.springframework.boot.autoconfigure.*` | 모듈별 `org.springframework.boot.<기술>.*` |
| `RestTemplate` | Framework 7에서 deprecated → **`RestClient`** |

- **의존성을 추가할 때마다 `-test` 짝을 함께 넣는다.** 누락 시 `@DataJpaTest` 같은 애노테이션이 예외 없이 조용히 동작하지 않는다

## 10. 개발 단계

> 순서 결정 원칙: **(1) 뒤 단계가 앞 단계에 의존하는 순서, (2) 되돌리기 비용이 큰 결정을 먼저, (3) 학습 곡선이 가파른 것을 앞쪽에.**

> 전 단계에 걸쳐 §1.4의 개발 원칙(DP-1 ~ DP-5)이 적용된다.

> ### 졸업선 (v1.3)
>
> **Phase 7 완료 = 학습 목표 달성 (졸업). Phase 8~10은 보너스다.**
>
> - 근거: Phase 6까지 G-3의 학습 목표가 배포를 제외하고 전부 커버되고, Phase 7은 Phase 6의 실전 검증 지점이자 G-2(Obsidian 이전)의 완결 지점이다
> - Phase 8(프론트)은 주력 분야라 사실상 놀이, Phase 9(배포)는 보너스 1순위, Phase 10은 원래 선택 항목
> - 졸업선의 목적은 중단이 아니라, Phase 8부터를 "보너스를 하는 중"이라는 감각으로 진행하기 위함이다. 습작이 "또 하나의 미완성 프로젝트"가 되는 것을 막는 심리적 장치다

### Phase 0 — 도메인 설계 ✅ 완료 (2026-08-18)

- **진행 방식: 개발자가 직접 설계하고, 리뷰를 받는다 (DP-5).**
- 산출물: 엔티티 18개 코드, 필드/타입, 연관관계와 주인, 제약 조건 — `docs/entity-design-v0.3.md`
- **이 단계에서 결정을 최대한 확정한다.** 엔티티 구조는 되돌리기 비용이 가장 크다
- 선행 확인 필요: ~~OI-05, OI-06, OI-13~~ → OI-06·OI-13 해소, OI-05는 Phase 1로 이관

#### 검증 방식 (v1.4 — 실제 수행 기록)

`ddl-auto: create`로 실행해 **생성된 DDL을 눈으로 확인**하는 절차를 두었고, 코드 리뷰만으로는 잡히지 않는 문제 3건을 여기서 발견했다.

| 발견 | 내용 |
|---|---|
| `@AttributeOverride`는 병합이 아니라 **교체** | `Money`에 준 `precision`/`length`가 사라져 `numeric(38,2)`, `varchar(255)`가 됨 |
| enum이 **H2 네이티브 `enum` 타입**으로 생성 | Hibernate 6.2+ 기본 동작. `@JdbcTypeCode(SqlTypes.VARCHAR)`로 `varchar` + `check` 제약으로 전환 |
| `preferred_enum_jdbc_type` 전역 설정 미적용 | 애노테이션 방식이 확실. **전역 설정은 먹으면 편한 것, 애노테이션은 확실한 것** |

> **원칙**: 엔티티를 추가·수정할 때마다 DDL을 확인한다. 매핑 애노테이션의 실제 효과는 코드만 봐서는 알 수 없다.

#### 확정된 화면 구성 (v1.5)

원래 12개로 나눴던 것을 사용자가 4개로 합쳤다.

| 화면 | 포함 | 비고 |
|---|---|---|
| 백로그 목록 | 검색·필터·정렬·페이징 + 태그 폴더 + 통계 | 통계(Phase 6)가 여기 붙는다 |
| 백로그 상세/편집 | 상세 + 개인기록·오버라이드·회차·취득·태그·장르 편집 | 폼이 여러 개인 한 화면 |
| 담기 | 게임 검색(IGDB, Phase 4) + 담기 | |
| 프로필/설정 | 프로필 + 플랫폼 계정 + 보유 기기 + 구독 | |

**목록 카드에 표시할 것**: 커버(없으면 기본) · 이름 · 장르 · 평점(있으면) · **마지막 회차**(번호 · 시작일 · 종료일 · 기기)

**태그는 카드에 뿌리지 않는다.** 폴더/모음집처럼 묶는 탐색 수단이다(§6.7). 따라서 **태그별 항목 수 집계**가 필요하다.

**정렬 4종** — 이름 · 평점 · 출시일 · 최근 플레이(기본). BR-QRY-01에 따라 2차 기준은 최근 플레이순.

#### API 방향 (v1.5 결정)

```
읽기   화면 단위로 한 번에    목록 카드가 5개 도메인을 걸치므로 리소스 단위로 쪼개면 호출이 폭발한다
쓰기   리소스 단위로 따로     한 화면에 폼이 5개면 엔드포인트도 5개. 검증도 각각 다르다
```

- 조합 지점은 **조회 전용 서비스**에 둔다. 컨트롤러에서 조합하면 `open-in-view: false`라 LAZY 접근이 터지고 NFR-A3(트랜잭션 안에서 DTO 변환)도 어긋난다
- 조회 전용 서비스는 **화면 단위로 하나씩** 둔다. 하나에 전부 넣으면 God object가 된다

#### 예상되는 N+1 지점

목록 카드 기준으로 다음 3방이면 끝나야 한다.

```
1방  항목 + 마지막회차 + 기기 + 커버   전부 ~ToOne이므로 join fetch (페이징 유지)
1방  개인 장르 (batch size)
1방  마스터 장르 (batch size)
```

`lastPlaythrough` 비정규화(§7.2)가 없으면 이 자리가 항목 수만큼의 쿼리가 된다.

**진행 원칙**: DP-1·DP-4 유지. SQL 로그를 켜둔 채 개발하고, 엔티티를 만지면 DDL을 확인한다.
