## 이 문서의 구조에 대하여 (학습 노트)

실무 기능 명세서는 대체로 아래 흐름을 따른다. 각 절이 왜 있는지 알아두면 남의 명세서를 읽을 때도 편하다.

| 절 | 존재 이유 |
|---|---|
| 범위(Scope) | **"안 만드는 것"을 명시**하는 게 핵심이다. 이게 없으면 개발 중에 요구가 무한히 늘어난다 |
| 용어 정의 | 같은 단어를 서로 다르게 쓰는 사고를 막는다. 실제로 이 프로젝트도 "유저"가 세 가지 뜻으로 쓰이고 있었다 |
| 액터/권한 | 누가 무엇을 할 수 있는지. 권한 설계의 출발점 |
| 기능 요구사항 | ID를 붙여 추적 가능하게 한다. 테스트 케이스와 1:1로 연결된다 |
| 비기능 요구사항 | 성능·보안·운영처럼 "기능은 아닌데 없으면 망하는 것" |
| 미결정 사항 | 모르는 걸 모른다고 적어두는 칸. **비워두면 나중에 잊는다** |

### 표기 규약

| 약어 | 원어 | 의미 |
|---|---|---|
| **FR** | Functional Requirement | 기능 요구사항 |
| **NFR** | Non-Functional Requirement | 비기능 요구사항 (성능·보안·운영) |
| **BR** | Business Rule | 비즈니스 규칙 / 검증 규칙 |
| **OI** | Open Issue | 미결정 사항 |

요구사항 ID는 `FR-{영역}-{번호}` 형식이다. 우선순위는 MoSCoW 기법을 따른다.

- **MUST** — 없으면 서비스가 성립하지 않음
- **SHOULD** — 중요하지만 없어도 동작함
- **COULD** — 여유가 되면

## 1. 개요

### 1.1 목적

개인이 소유·플레이한 게임을 기록하고, 진행 상태·평가·지출을 관리하는 백로그 서비스를 개발한다.

### 1.2 프로젝트 성격

본 프로젝트는 **Spring Boot / JPA 학습을 위한 습작**이다. 상업적 서비스화를 하지 않기로 확정했으며, 이에 따라 다음이 성립한다.

- 저작권·API 상업 이용 약관·개인정보 처리방침 관련 요구사항을 다루지 않는다
- 실사용자는 개발자 본인 1명을 전제로 하되, **구조는 다중 사용자를 가정해 설계**한다 (학습 목적)
- 기능 개수를 늘리기보다 **기술 스펙트럼의 깊이**를 우선한다

### 1.3 학습 로드맵상의 위치

```
① JPA 기본편 핵심 개념   → 대화로 압축 학습
② JPA 활용 1편           → 강의 직접 (남의 완성 프로젝트 관통)
③ 습작 데모 서비스        ← 【본 프로젝트】
④ 실서비스 (Brankit / JADU)
```

본 프로젝트는 **③ 습작 데모 단계**이며, 활용편(남이 설계한 프로젝트)과 실서비스 사이의 **완충지대**다.

- ~~활용 1편에는 "내가 설계하고 부딪히는" 경험이 빠져 있다. 그 공백을 메우는 것이 본 프로젝트의 존재 이유다~~
- DTO 변환·예외 처리·보안·배포는 **따로 배우면 붙지 않고, 돌아가는 코드에 하나씩 얹어야 붙는 주제**다. 그래서 완성된 도메인 위에 단계적으로 쌓는 구성을 취한다
- **"습작 데모까지가 학습, 실서비스부터가 개발"** — 이 경계가 로드맵의 핵심이며, 본 프로젝트는 학습 쪽에 속한다

### 1.5 목표 (Goals)

- G-1. 개인 게임 기록의 완전한 CRUD와 조회/통계
- G-2. 기존 Obsidian 기록의 이전(마이그레이션)
- G-3. 학습 목표 달성: 연관관계 설계, N+1 대응, 트랜잭션 경계, 인증/인가, 외부 API 연동, 파일 업로드, 배치, 배포

### 1.6 비목표 (Non-Goals)

- 상업적 운영 및 수익화
- 소셜 기능 (팔로우, 공유, 댓글, 랭킹)

- 플레이 시간 자동 측정 (Steam 연동 등)

## 2. 용어 정의

| 용어 | 정의 |
|---|---|
| **회원 (Member)** | 로그인하는 서비스 계정 |
| **게임 마스터 (Game)** | 게임 자체의 객관적 정보. 전체 회원이 공유한다. RAWG API에서 가져오거나 수동 등록한다 |
| **백로그 항목 (BacklogEntry)** | 특정 회원이 특정 게임에 대해 갖는 개인 기록. 회원과 게임 마스터를 잇는 조인 엔티티다 |
| **오버라이드 (Override)** | 게임 마스터의 값을 개인이 덮어쓴 값. 값이 있으면 그것을, 없으면 마스터 값을 표시한다 |
| **회차 (Playthrough)** | 한 게임을 처음부터 끝까지(또는 중단까지) 플레이한 1회 단위 |
| **플랫폼 (Platform)** | 게임 유통·계정 체계. Steam, Nintendo, PSN, Xbox, GOG, Epic, 실물 등 |
| **플랫폼 계정 (PlatformAccount)** | **회원이 특정 플랫폼에서 보유한 계정.** 예: Steam의 "Beene", Steam의 "Ryan", Nintendo의 "Beene" |
| **기기 (Device)** | 게임을 실제로 실행한 하드웨어 또는 에뮬레이터. Switch 2, Windows PC, Steam Deck, Mac, Ryujinx 등 |
| **취득 (Acquisition)** | 게임을 손에 넣은 방식·경로·금액 |

> **핵심 구분 1 — 플랫폼 계정 ≠ 사람**
> "Beene", "Ryan"은 **계정 라벨**이다. 한 사람이 Steam 계정 두 개를 가질 수 있고, 같은 이름의 계정이 Steam과 Nintendo에 각각 있을 수 있다. 함께 플레이한 사람에 대한 기록은 **태그**로 처리한다.

> **핵심 구분 2 — 플랫폼 ≠ 기기**
> Steam에서 산 게임을 Windows PC로 할 수도, Steam Deck으로 할 수도 있다. 구매 경로(플랫폼)와 실행 환경(기기)은 별개 축이다.

## 3. 범위

### 3.1 포함 (In Scope)

- 회원 가입/로그인/세션 관리, 이메일 인증, 비밀번호 재설정
- Google OAuth 연동 (계정 연결 방식)
- 회원 탈퇴 및 유예 기간 처리
- 게임 마스터 관리 (RAWG 연동 + 수동 등록)
- 백로그 항목 CRUD 및 개인 오버라이드
- 회차 기록 및 검증
- 플랫폼 계정 및 보유 기기 관리
- 취득 정보 및 구독 관리
- 개인 태그
- 목록 조회 (검색/필터/정렬/페이징)
- 통계 (장르, 기간, 지출, 플레이타임)
- 커버 이미지 업로드 (개인 소유)
- Obsidian YAML 임포트
- 관리자 기능 및 감사 로그
- 변경 이력 및 소프트 삭제
- 배포 (Render + Neon + Vercel)

### 3.2 명시적 제외 (Out of Scope)

| 제외 항목 | 사유 |
|---|---|
| DLC를 독립 게임으로 관리 | 본편의 회차 + **별도 취득 기록**으로 흡수 (v1.3). API 호출도 하지 않음 |
| 시리즈/프랜차이즈 묶음 | 학습 가치 대비 복잡도 과다 |
| 위키형 공동 편집 (편집 이력·롤백·반달 방지) | **단독 프로젝트 규모**. 습작 범위를 초과함 |
| 게임 별칭(aliases) 필드 | 개인 오버라이드 이름이 검색 대상이 되므로 불필요 |
| DLC 등록 대기 큐 / 승인 워크플로 | 관리자 = 개발자 본인. 실익 없음 |
| 카카오 로그인 | OAuth2 비표준이라 커스텀 코드 대비 학습량이 낮음 |
| 지역별 출시일 | 가장 이른 출시일 하나만 사용 |
| 플레이 시간 자동 측정 | 수동 정수 입력으로 대체 |
| 위시리스트 별도 개념 | 미구매 + 미플레이 상태로 판단 |
| "함께 플레이한 사람" 전용 엔티티 | 태그로 대체 |
| 스크린샷/영상 | 파일 저장 인프라가 커버와 동일하므로 마지막 단계에서 재검토 |

## 4. 액터 및 권한

| 액터 | 설명 | 권한 |
|---|---|---|
| **비로그인 사용자** | 미인증 방문자 | 가입, 로그인, 비밀번호 재설정 요청만 가능 |
| **회원** | 인증된 일반 사용자 | 자신의 백로그 데이터 전체 CRUD, 게임 마스터 신규 등록 |
| **탈퇴 유예 회원** | 탈퇴 요청 후 30일 이내 | **인증은 통과하되 인가는 제한.** 복구 확인 화면만 접근 가능 |
| **관리자** | 단일 계정 | 무제한. 마스터 수정/병합, 전체 조회 |

### 4.1 권한 설계 원칙

- **AUTH-P1.** 관리자는 현재 권한 제약이 없다. 단, **모든 관리자 행위는 감사 로그로 기록**한다.
  - 근거: 권한 제약은 나중에 조일 수 있지만, 감사 로그는 소급 생성이 불가능하다.
  - 감사 로그는 **데이터 변경뿐 아니라 조회 행위도 기록**한다. "볼 수는 있되 본 기록이 남는다"가 개인정보 통제의 실질적 수단이다.
- **AUTH-P2.** 게임 마스터의 최초 등록은 회원이, 등록 이후 수정은 관리자만 할 수 있다.
  - 회원은 마음에 들지 않는 마스터 값을 **개인 오버라이드로 덮어** 사용한다.
- **AUTH-P3.** 비밀번호는 단방향 해시로 저장한다. 관리자도 원문을 볼 수 없다. (알고리즘 미정 — OI-03)

## 5. 도메인 모델 개요

```
Member ──1:N── BacklogEntry ──N:1── Game (마스터, 전체 공유)
  │                  │
  │                  ├──1:N── Playthrough (회차)
  │                  │            ├── Device          (실행 기기)
  │                  │            └── PlatformAccount (플레이 계정)
  │                  │
  │                  ├──1:N── Acquisition (취득: 방식 + 계정 + 금액 — 재구매·DLC로 복수 가능)
  │                  ├──N:M── Tag        (개인 태그)
  │                  ├──N:M── Genre      (개인 장르 — 태그와 동일 메커니즘)
  │                  └── CoverImage      (개인 소유)
  │
  ├──1:N── PlatformAccount ──N:1── Platform (마스터)
  ├──1:N── Subscription    (구독 이력)
  └──N:M── Device          (보유 기기 — 입력 기본값 용도)
```

### 5.1 엔티티 책임

| 엔티티 | 책임 | 소유 |
|---|---|---|
| `Game` | 게임의 객관적 사실 (이름, 개발사, 퍼블리셔, 장르, 출시일, 정가) | 전체 공유 |
| `BacklogEntry` | "나의 기록" 전체를 묶는 루트 | 개인 |
| `Playthrough` | 1회 플레이의 기간·상태·환경 | 개인 |
| `Acquisition` | 취득 방식·경로·금액 | 개인 |
| `Subscription` | 구독 서비스 가입 이력과 요금 | 개인 |
| `Platform` | 유통·계정 체계 마스터 | 전체 공유 |
| `PlatformAccount` | 회원이 보유한 플랫폼별 계정 | 개인 |
| `Device` | 실행 기기 마스터 | 전체 공유 |
| `Tag` | 개인 태그 (사전 메커니즘 — §6.7) | 개인 |
| `Genre` | 개인 장르 (태그와 동일한 사전 메커니즘 — §6.7) | 개인 |
| `CoverImage` | 커버 이미지 URL·메타데이터 | 개인 |

### 5.2 핵심 설계 결정 ①: 마스터 + 오버라이드

**결정**: 게임 마스터는 고정하고, 개인 수정값은 백로그 항목에 별도 저장한다.

**표시 규칙**: `표시값 = 개인 오버라이드 ?? 마스터 값` (오버라이드를 지우면 마스터 값이 다시 표시됨)

**대안 검토 기록**

| 대안 | 채택 | 사유 |
|---|---|---|
| 마스터 고정 + 개인 오버라이드 | **채택** | 데이터 중복 없음, 마스터 갱신 시 전체 반영 |
| 담을 때 마스터를 개인별로 복사 | 기각 | 회원 수만큼 데이터 복제, 학습 가치 낮음 |

**오버라이드 대상 필드**: 게임명, 개발사, 퍼블리셔, 출시일, 정가

> **장르는 오버라이드 필드가 아니다 (v1.3).** 개인 장르 사전(§6.7)으로 처리한다. 의미는 같은 `개인값 ?? 마스터값`이되, 문자열 컬럼이 아니라 사전 엔티티 구조다.

> **비용 인식**: 이 방식은 조회 시 `COALESCE(개인값, 마스터값)` 형태가 되어 인덱스가 동작하지 않는다. §7.2에서 비정규화로 해결한다.

### 5.3 핵심 설계 결정 ②: 플랫폼 / 계정 / 기기의 3축 분리

**결정**: 유통 체계(Platform), 계정(PlatformAccount), 실행 환경(Device)을 각각 분리한다.

| 축 | 예시 | 붙는 위치 |
|---|---|---|
| Platform | Steam, Nintendo, PSN, Xbox, GOG, Epic, 실물 | 마스터 |
| PlatformAccount | Steam/"Beene", Steam/"Ryan", Nintendo/"Beene" | 취득 정보, 회차 |
| Device | Windows PC, Steam Deck, Mac, Switch 2, Ryujinx | 회차 |

**시나리오 검증**

```
Steam의 "Ryan" 계정으로 구매  → Acquisition.platformAccount
1회차: Windows PC로 플레이     → Playthrough.device
2회차: Steam Deck으로 플레이   → Playthrough.device
```

**대안 검토 기록**

| 대안 | 채택 | 사유 |
|---|---|---|
| 구매처(Store)를 Platform과 별도 엔티티로 | 기각 | Steam은 구매처이자 계정 체계다. 분리할 근거가 없고 엔티티만 늘어난다 |
| 계정을 회차에만 두기 | 기각 | "어느 계정으로 샀나"가 취득 정보의 핵심이다 |
| Platform / PlatformAccount / Device 3축 | **채택** | 실제 사용 시나리오와 일치. 통계 축이 셋으로 늘어남 |

#### 상세 규칙

**FR-AUTH-02 이메일 인증**
- 인증 토큰: 랜덤 문자열, 만료 시각 보유, **1회용**(사용 즉시 폐기)
- 토큰은 **해싱하여 저장**한다. DB가 유출돼도 토큰을 사용할 수 없어야 한다
- 미인증 상태에서 재발송을 요청할 수 있다

**FR-AUTH-05 비밀번호 재설정**
- 토큰 구조는 FR-AUTH-02와 동일하다 (랜덤 / 만료 / 1회용 / 해싱 저장)
- **계정 존재 여부를 노출하지 않는다.** 가입 여부와 무관하게 동일한 응답을 반환한다
  - 근거: 응답이 다르면 가입자 이메일 목록을 열거할 수 있다
- 재설정 성공 시 기존 세션을 전부 무효화한다

**FR-AUTH-06~08 Google 계정 연동**

- **연결은 로그인된 상태에서만 가능하다.**

| 방식 | 채택 | 사유 |
|---|---|---|
| 이메일 동일 시 자동 연결 | 기각 | 공격자가 타인 이메일로 선점 가입 시 계정 탈취 가능 |
| 별도 계정으로 취급 | 기각 | 데이터 분리로 사용성 저하 |
| 로그인 상태에서 수동 연결 | **채택** | 실무 표준, 학습 가치 |

- **BR-AUTH-01**: 비밀번호가 설정되지 않은 계정은 소셜 연결을 해제할 수 없다 (로그인 수단 소멸 방지)

**FR-AUTH-09~10 탈퇴 유예**
- 탈퇴 요청 시 `deletedAt`을 기록한다 (소프트 삭제)
- 유예 기간 30일. 경과 후 **스케줄 배치가 물리 삭제**한다
- 유예 중 로그인 시 **인증은 성공하되 인가를 제한**하여 복구 확인 화면으로 유도한다
- **BR-AUTH-02**: 이메일/아이디는 유예 기간 중 재사용할 수 없다 (유니크 제약 유지)

### 6.2 게임 마스터 (GAME)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-GAME-01 | RAWG API로 게임을 검색할 수 있다 | MUST |
| FR-GAME-02 | 검색 결과를 선택하면 게임 마스터에 저장한다 (온디맨드 캐시) | MUST |
| FR-GAME-03 | 이미 마스터에 있는 게임은 API를 호출하지 않고 재사용한다 | MUST |

| FR-GAME-05 | 마스터 정보를 RAWG와 재동기화할 수 있다 | COULD |

#### 마스터 필드

| 필드 | 출처 | 비고 |
|---|---|---|
| 원본 게임명 (영문) | RAWG / 수동 | 오버라이드되어도 원본은 유지 |
| 개발사 (복수) | RAWG / 수동 | |
| 퍼블리셔 (복수) | RAWG / 수동 | |
| 장르 (복수) | RAWG / 수동 | 참고값. 개인 장르가 없을 때의 표시·집계 폴백 (§6.7) |
| 출시일 | RAWG의 플랫폼별 출시일 중 **가장 이른 날짜** | |
| 정가 | **수동 입력** | RAWG는 가격 데이터를 제공하지 않음 |
| `source` | `RAWG` \| `MANUAL` | |
| `externalId` | RAWG 게임 ID | `MANUAL`인 경우 null |
| `lastSyncedAt` | 마지막 동기화 시각 | 재동기화 판단 기준 |

- **커버 이미지 필드는 마스터에 두지 않는다.** 커버는 개인 소유다 (§6.9)
- **모든 필드는 null을 허용한다.** 정보가 없는 상태를 정상으로 취급한다

#### 상세 규칙

**FR-GAME-02 온디맨드 캐시 흐름**

```
검색 → 마스터에 존재?
        ├─ 있음 → 그대로 사용 (API 호출 0회)
        └─ 없음 → RAWG 상세 호출 → 마스터 저장 → 사용
```

근거: 전체 게임을 미리 저장할 수 없고, 실제로 담기는 게임은 일부다. API 호출량·성능·외부 장애 내성을 동시에 확보한다.

**FR-GAME-04 수동 등록**
- 최초 등록자가 마스터 값을 채운다
- **등록 이후 수정은 관리자만 가능하다** (AUTH-P2)
- 임포트 시 RAWG 매칭에 실패한 게임도 이 경로로 처리한다

**FR-GAME-05 재동기화**
- `lastSyncedAt` 기준 일정 기간 경과 시 재조회한다
- **개인 오버라이드는 재동기화의 영향을 받지 않는다**

| FR-BL-03 | 마스터 값을 개인 오버라이드로 수정할 수 있다 | MUST |
| FR-BL-04 | 오버라이드를 삭제하면 마스터 값이 다시 표시된다 | MUST |
| FR-BL-05 | 평점을 기록할 수 있다 | MUST |
| FR-BL-06 | 총 플레이 시간을 기록할 수 있다 | MUST |
| FR-BL-07 | 평가/메모를 마크다운으로 작성할 수 있다 | MUST |
| FR-BL-08 | 백로그 항목을 삭제할 수 있다 (소프트 삭제) | MUST |
| FR-BL-09 | 변경 이력을 조회하고 되돌릴 수 있다 | SHOULD |

#### 필드 정의

| 필드 | 타입/제약 |
|---|---|
| 평점 | `BigDecimal`, **0.0 ~ 100.0, 소수점 1자리** |
| 플레이 시간 | 정수(시간 단위), **수동 입력** |
| 평가/메모 | 마크다운 텍스트 |
| 개인 커버 | 이미지 URL (§6.9) |

> **평점 타입 주의**: `double`은 부동소수점 오차로 84.3을 정확히 저장하지 못한다. 정렬·비교가 미묘하게 어긋나므로 **`BigDecimal`을 사용한다.** 금액도 동일하다.

#### 상세 규칙

**FR-BL-02 중복 방지**
- **DB 유니크 제약** `(member_id, game_id)`로 보장한다
- 애플리케이션 검증만으로는 동시 요청을 막을 수 없다 (조회→판단→저장이 원자적이지 않음)
- 제약 위반 시 409 Conflict로 응답한다

**FR-BL-09 변경 이력 — 스냅샷 방식 (v1.3)**
- 대상: **`BacklogEntry`와 `Playthrough`만**. 그 외 엔티티는 이력을 남기지 않는다
- 방식: 필드 단위 델타가 아니라 **변경 시점의 엔티티 상태 전체를 JSON으로 저장**한다
  - 델타 방식은 되돌릴 때 문자열 이전값을 필드마다 타입 복원해야 한다. 스냅샷은 역직렬화로 끝난다
  - "무엇이 바뀌었나" 표시가 필요하면 인접 스냅샷을 비교해 계산한다
- **되돌리기는 복원 "시도"다.** 무조건 성공하는 연산이 아니다
  - 스냅샷 상태가 현재의 검증 규칙(BR-PT-01~04 등)을 통과해야 커밋한다
  - 스냅샷이 참조하는 대상(기기, 계정 등)이 삭제되었으면 실패 처리한다
  - 복원 후 비정규화 컬럼(§7.2)을 재계산한다
- Hibernate Envers는 채택하지 않는다 — 동작이 은폐되어 학습 목적에 맞지 않음

DLC는 별도 게임으로 관리하지 않고 **본편의 추가 회차로 흡수**한다.

```
1회차  2026-05-01 ~ 2026-06-20   (본편)
2회차  2026-10-05 ~ 2026-11-02   라벨: "DLC - 쿠파 왕국"
```

- DLC 구매 금액은 본편 백로그 항목에 **별도 취득 기록으로 남긴다** (v1.3 — 합산 방식 폐기). 취득 라벨로 구분한다. 예: `"DLC - 쿠파 왕국"`
- RAWG의 DLC 엔드포인트는 호출하지 않는다

#### 기기 선택 규칙

- **BR-PT-05**: 회차의 기기는 `Device` 마스터 전체에서 선택할 수 있다. 회원의 보유 기기 목록은 **입력 편의를 위한 우선 표시일 뿐 제약이 아니다.**

### 6.6 취득 및 지출 (ACQ)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-ACQ-01 | 백로그 항목에 취득 방식을 기록한다 | MUST |
| FR-ACQ-02 | 취득에 사용한 플랫폼 계정을 기록한다 | MUST |
| FR-ACQ-03 | 구매 금액을 통화와 함께 기록한다 | MUST |
| FR-ACQ-04 | 구독 서비스 가입 이력을 관리한다 | SHOULD |
| FR-ACQ-05 | 취득 방식이 구독인 경우 해당 구독을 연결한다 | SHOULD |
| FR-ACQ-06 | 동일 게임에 취득 기록을 여러 건 남길 수 있다 (재구매, DLC) | MUST |

#### 취득 방식 (enum)

`PURCHASED` | `SUBSCRIPTION` | `FREE` | `GIFT` | `BORROWED` | `DEMO` | `NOT_OWNED`

- `NOT_OWNED` + 회차 없음 = 사실상 위시리스트. **별도 개념을 두지 않는다**
- 실물 구매 등 계정이 없는 경우 `PlatformAccount`는 null이며 `Platform`만 기록할 수 있다

#### 취득 카디널리티 (v1.3)

- `Acquisition`은 **별도 엔티티**이며 `BacklogEntry`와 **1:N**이다 (임베디드 미채택 — §13 미결 해소)
- 근거 시나리오: 같은 게임을 Steam으로 샀다가 Switch판으로 **재구매**하는 경우. 백로그 항목은 `(member, game)`당 1개이므로 취득이 복수여야 담긴다
- DLC 구매도 별도 취득 행이다 (§6.4)
- 취득에 **라벨**(자유 문자열, nullable)을 둔다. 예: `"스위치판 재구매"`, `"DLC - 쿠파 왕국"`
- BR-ACQ-01의 "게임 구매 금액 합계"는 모든 취득 행의 합이다

#### 금액 표현

- `Money` 값 타입 (`@Embeddable`): `amount`(`BigDecimal`) + `currency`
- **통화는 ISO 4217 코드 문자열로 저장한다.** enum을 쓰지 않는다 — 나중에 통화를 늘릴 때 스키마 변경이 필요 없다
- 초기 지원 통화: KRW, USD, JPY
- **저장은 항상 입력한 원본 통화 기준**이다

#### 구독 (Subscription)

| 필드 | 비고 |
|---|---|
| 서비스명 | 예: Xbox Game Pass. **문자열로 저장한다** (OI-06 해소 — v1.4) |
| 시작일 / 종료일 | |
| 요금 | `Money` |
| 결제 주기 | 월 / 연 |

> **OI-06 결정 근거 (v1.4)**: 서비스명을 마스터 엔티티로 두지 않는다. 다른 엔티티가 참조하지 않고, 통계 축도 아니며(지출은 §6.6의 두 축으로만 집계), 자동완성이 필요하면 기존 구독 이력에서 `DISTINCT`로 뽑으면 충분하다. 엔티티화의 이득이 없다.

#### 지출 집계 원칙

- **BR-ACQ-01**: 구독료는 개별 게임에 배분하지 않는다. 총 지출은 두 축으로 분리해 집계한다.

```
총 지출 = 게임 구매 금액 합계 + 구독료 합계
```

대안 검토: 구독 기간 중 플레이한 게임 수로 나누는 방식은 배분 기준이 자의적이라 기각.

### 6.7 태그와 개인 장르 (TAG)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-TAG-01 | 백로그 항목에 개인 태그를 붙일 수 있다 | MUST |
| FR-TAG-02 | 태그 이름을 변경하거나 삭제할 수 있다 | MUST |
| FR-TAG-03 | 태그로 필터링하여 조회할 수 있다 | MUST |
| FR-TAG-04 | 입력 시 기존 태그/장르를 자동완성으로 추천한다 | SHOULD |
| FR-TAG-05 | 개인 장르는 태그와 동일한 사전 메커니즘을 따른다 | MUST |

#### 사전(Dictionary) 메커니즘 (v1.3)

태그와 개인 장르는 **IntelliJ 사전과 같은 방식**으로 동작한다.

- **등록 절차가 없다.** 항목에 적으면 목록에 생긴다
- **자동완성**: 다른 항목에서 입력할 때 기존 목록을 추천으로 보여준다
- **자동 소멸**: 어떤 백로그 항목에도 연결되지 않게 되면 목록에서 사라진다. **삭제 시점은 연결 해제 즉시다** (OI-13 해소 — v1.4)
  - **구현 (v1.5 개정)**: 사전 행을 지우지 않는다. **조회에서 연결이 1건 이상인 것만 반환**한다. 연결을 뗄 때는 연결 행만 삭제하고 사전 행은 그대로 둔다
  - 개정 근거: 기존 방식(COUNT → 0이면 DELETE)은 읽고-쓰기 사이에 경쟁 상태가 있었다. 두 요청이 동시에 마지막 연결을 떼면 둘 다 0을 보고 둘 다 지우려 든다. 조회에서 거르면 경쟁 대상 자체가 사라지고, **지연도 0이라 "즉시 사라진다"를 그대로 만족**한다
  - 부수 효과: 뗐던 태그를 다시 붙이면 **원래 행을 재사용**한다. 새 행을 만들지 않으므로 유니크 제약과 충돌하지 않는다
  - 감수: 연결이 0인 행이 테이블에 남는다. 조회에 안 잡히므로 기능상 무해하며, 정리가 필요해지면 그때 청소 쿼리를 둔다 (배치 지연이 문제되지 않는다 — 어차피 보이지 않는다)
  - **`orphanRemoval`이나 `CascadeType.REMOVE`로는 불가능하다.** 하나의 `Tag`를 여러 `BacklogEntry`가 공유하므로 부모가 하나로 특정되지 않는다
  - 배치 **정리**를 소멸 수단으로 택하지 않은 이유: 자동완성 목록에 "쓰지 않는 태그"가 배치 주기만큼 남아 보이는 것이 사전 메커니즘의 취지에 어긋난다. 위 조회 필터는 이 문제가 없다
- 검색·필터의 옵션 목록은 이 사전이 기준이다
- UI에서 태그는 폴더처럼 표시할 수 있다 (데이터 구조는 평면, 표현만 폴더)

#### 태그 vs 장르

메커니즘은 같고 **용도(통계 축)가 다르다.**

| 구분 | 장르 | 태그 |
|---|---|---|
| 용도 | 게임 분류, 장르별 통계(FR-STAT-01) | 자유 분류 — 폴더, 함께 플레이한 사람 등 |
| 마스터와의 관계 | 개인 장르가 1개 이상이면 개인 장르를, 없으면 마스터(RAWG) 장르를 표시·집계에 사용 | 마스터 없음 |

- 태그·장르 모두 **회원 소유**다. 다른 회원과 공유하지 않는다
- 유니크 제약: `(member_id, name)` — 태그·장르 각각
- 계층 구조(폴더 트리)는 두지 않는다. 평면으로 시작한다
- 마스터(RAWG) 장르는 참고값으로 유지되며, 개인 사전과 섞이지 않는다
- 용도 예시(태그): `"친구와 함께한 게임"`, `"명작"` / (장르): `"세미 오픈 월드"`, `"플랫포머"`

### 6.8 조회 (QRY)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-QRY-01 | 백로그 목록을 페이징하여 조회한다 | MUST |
| FR-QRY-02 | 게임명으로 검색한다 | MUST |
| FR-QRY-03 | 상태·태그·장르·기기·플랫폼 계정으로 필터링한다 | MUST |
| FR-QRY-04 | 이름·평점·출시일·최근 플레이순으로 정렬한다 | MUST |
| FR-QRY-05 | 백로그 항목 상세를 조회한다 | MUST |

#### 상세 규칙

- **검색/정렬 대상은 비정규화 컬럼이다** (§7.2). 오버라이드와 마스터를 매번 합성하지 않는다
- **정렬 기본값**: 최근 플레이순
- **BR-QRY-01**: 동점 시 2차 정렬 기준은 최근 플레이순으로 한다
  - 2차 기준을 정하지 않으면 정렬 결과가 매 요청마다 달라져 페이징이 깨진다
- 응답은 **반드시 DTO로 변환**한다. 엔티티를 직접 반환하지 않는다
- 장르·태그 필터의 옵션 목록은 **개인 사전**(§6.7) 기준이다

#### 우선순위와 감수 사항

- **본 기능군의 우선순위는 `필터링·정렬 > 검색`이다.** 게임 수가 늘어도 태그·상태·장르로 좁히는 쪽이 실사용 빈도가 높다
- **한글 검색 범위**
  - 검색 대상은 `displayName`(개인 오버라이드 이름 ?? 마스터 원본명)이다. **이미 담은 게임은 한글로 적어두면 한글로 검색된다**
  - 반면 **아직 담지 않은 게임을 RAWG에서 찾을 때는 영문으로 검색해야 한다.** RAWG가 한글 데이터를 제공하지 않기 때문이며, 이는 **해결하지 않고 감수하는 제약**이다 (별칭 필드를 두지 않기로 한 결정과 연결됨 — §3.2)

#### 성능 요구 (N+1 대응)

목록 조회는 `Game`, `Playthrough`, `Tag` 등 다수의 연관을 함께 필요로 하므로 N+1이 발생하기 쉽다.

- `~ToOne` 연관 → **fetch join**
- 컬렉션(`~ToMany`) → **지연 로딩 + batch size**
  - 컬렉션 fetch join은 행이 증폭되고, **페이징이 불가능해진다** (전체를 메모리에서 자르므로 OOM 위험)
- 모든 `~ToOne` 연관은 `FetchType.LAZY`를 **명시**한다

### 6.10 커버 이미지 (MED)

| ID | 요구사항 | 우선순위 |
|---|---|---|

#### 상세 규칙

- **업로드 방식: presigned URL**
  - 서버는 "이 경로에 제한 시간 동안 업로드해도 좋다"는 서명된 URL만 발급하고, 파일은 브라우저에서 스토리지로 직접 전송한다
  - 근거: 서버 경유 시 메모리 압박(무료 티어 512MB)과 요청 점유 시간 증가
- **검증**: 확장자, MIME 타입, 최대 용량. 이미지로 위장한 파일을 차단한다
- **정리**: 커버 교체·삭제 시 기존 파일을 스토리지에서 제거한다

### 6.11 데이터 임포트 (IMP)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-IMP-01 | Obsidian YAML frontmatter 파일을 업로드하여 일괄 등록한다 | SHOULD |
| FR-IMP-02 | 건별로 성공/실패를 처리하고 실패 목록을 리포트한다 | SHOULD |
| FR-IMP-03 | RAWG 매칭 실패 건은 수동 등록 경로로 처리한다 | SHOULD |

#### 원본 데이터 형식

```yaml
---
created: 2025-12-13
cover: 00. System/Assets/Game/cover-super-mario-odyssey.jpg
developer:
  - Nintendo
  - 1-UP Studio
genre:
  - 플랫포머
  - 액션
  - 세미 오픈 월드
  - 어드벤처
price: 64800
releaseDate: 2017-12-01
link:
  - "[[게임 플레이]]"
playOn:
  - Nintendo Switch
startPlayDate: 2023-12-31
finishPlayDate: 2024-01-01
replays:
  - 2026-02-08~2026-02-08
  - 2026-06-04~2026-06-10
myRate: 94
---

(이하 본문 — 파싱하지 않음)
```

- **BR-IMP-01**: 파싱 대상은 파일 최상단 `---` ~ `---` 사이의 YAML 블록뿐이다. **그 아래 본문은 무시한다.**
  - 본문을 평가/메모 필드로 가져올지 여부는 미정 (OI-09)

#### 필드 매핑 규칙

| YAML 키 | 매핑 대상 | 처리 |
|---|---|---|
| `created` | 항목 생성일 | 그대로 |
| `cover` | — | **버림** (로컬 경로라 서버에서 무의미) |
| `developer` | 개발사 **개인 오버라이드** | API 표기와 달라도 오버라이드로 처리 |
| `genre` | **개인 장르 사전** (§6.7) | 한글 장르 그대로 개인 장르로 생성·연결. 표준 장르로 매핑하지 않음 |
| `price` | 취득 금액 | **구매가, 통화 KRW** |
| `releaseDate` | 출시일 **개인 오버라이드** | 마스터와 충돌해도 오버라이드 우선 |
| `link` | — | **버림** (Obsidian 내부 링크) |
| `playOn` | 회차의 실행 기기 | |
| `startPlayDate` / `finishPlayDate` | **1회차** | |
| `replays` | 2회차 이후 | `시작~종료` 형식. `~` 뒤가 비면 **진행 중** |
| `myRate` | 평점 | **0.0 ~ 100.0 스케일** |

- 플랫폼 계정 정보는 원본에 없으므로 임포트 후 수동 보정한다

#### 트랜잭션 전략

- **BR-IMP-02**: 행(파일) 단위로 트랜잭션을 분리한다. 전체를 하나로 묶지 않는다
  - 파일 전체를 한 트랜잭션으로 묶으면 1건 실패 시 전부 롤백된다
  - 건별 분리 시 성공한 건은 유지되고 실패 목록만 리포트된다
- 실패 리포트에는 **파일명과 실패 사유**를 포함한다
- 롤백 기능은 제공하지 않는다

> **구현 주의**: 같은 클래스 내부에서 메서드를 호출하면 `@Transactional`이 적용되지 않는다(프록시를 거치지 않으므로). "루프 안에서 건별 트랜잭션"은 이 함정이 정확히 발생하는 지점이다.

#### 임포트 시에도 적용되는 검증

- BR-PT-01 ~ BR-PT-04 전부 적용된다
- 특히 BR-PT-03(진행 중 회차 1개)에 걸리는 과거 데이터가 있을 수 있다

#### 예외 케이스 처리

| ID | 케이스 | 처리 |
|---|---|---|
| **BR-IMP-03** | `replays`는 있으나 `startPlayDate`가 없음 | **해당 파일을 실패 처리하고 리포트에 사유를 남긴 뒤 다음 파일로 넘어간다.** 회차 번호를 임의로 추정하지 않는다 |
| BR-IMP-04 | 게임명으로 RAWG 매칭 실패 | 실패 리포트에 남기고, 수동 등록 경로(FR-GAME-04)로 처리하도록 안내한다 |
| BR-IMP-05 | 회차 검증(BR-PT-01~04) 위반 | 해당 파일을 실패 처리하고 위반한 규칙 ID를 리포트에 명시한다 |
| BR-IMP-06 | frontmatter 자체가 없거나 파싱 불가 | 해당 파일을 실패 처리하고 넘어간다 |

- 모든 실패는 **파일 단위로 격리**된다. 한 건의 실패가 다른 파일의 처리를 막지 않는다 (BR-IMP-02)

### 6.13 공통/시스템 (SYS)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-SYS-01 | 모든 엔티티는 생성/수정 일시를 자동 기록한다 | MUST |
| FR-SYS-02 | 삭제는 엔티티별 삭제 정책(§7.4)을 따른다 — 소프트/되살리기/물리 | MUST |
| FR-SYS-03 | 예외를 일관된 HTTP 상태코드와 응답 형식으로 변환한다 | MUST |
| FR-SYS-04 | 외부 API 장애 시 작업을 취소하고 서버 로그에 기록한다 | MUST |
| FR-SYS-05 | 초기 시드/테스트 데이터를 제공한다 | SHOULD |
| FR-SYS-06 | 탈퇴 유예 만료 계정을 배치로 물리 삭제한다 | MUST |

- **FR-SYS-01**: JPA Auditing + 공통 `BaseEntity`
- **FR-SYS-03**: `@RestControllerAdvice` 기반 글로벌 예외 처리. 예) 유니크 제약 위반 → 409
- **FR-SYS-04**: RAWG 장애 시 사용자에게 실패를 알리고 취소한다. 부분 저장하지 않는다
- **FR-SYS-06**: `@Scheduled` 기반 배치
- **입력값은 프론트엔드 검증과 무관하게 서버에서 재검증한다**

## 7. 데이터 규칙

### 7.1 오버라이드 규칙

```
표시값 = COALESCE(개인 오버라이드, 마스터 값)
```

- 오버라이드를 null로 지우면 마스터 값이 다시 표시된다
- 마스터 재동기화는 오버라이드에 영향을 주지 않는다

### 7.2 비정규화 컬럼 (의도적 정규화 위반)

`BacklogEntry`는 조회 성능을 위해 파생값을 컬럼으로 보관한다.

| 컬럼 | 파생 원천 | 갱신 시점 |
|---|---|---|
| `displayName` | 이름 오버라이드 ?? 마스터 원본명 | 오버라이드 변경 시 |
| `status` | 취득 방식 + 최신 회차 상태 (§7.6) | 회차/취득 변경 시 |
| `lastPlayedAt` | 최신 회차의 종료일(또는 시작일) | 회차 변경 시 |

**근거**: 매 조회마다 `COALESCE(...)`나 서브쿼리로 계산하면 인덱스가 동작하지 않고, 필터·정렬·페이징 성능이 무너진다. 정규화를 의도적으로 깨는 대신 **갱신 책임을 서비스 계층이 진다.**

### 7.3 유니크 제약

| 대상 | 제약 | 목적 |
|---|---|---|
| `BacklogEntry` | `(member_id, game_id)` | 같은 게임 중복 담기 방지 |
| `Tag` | `(member_id, name)` | 태그 이름 중복 방지 |
| `Genre` | `(member_id, name)` | 개인 장르 이름 중복 방지 |
| `PlatformAccount` | `(member_id, platform_id, account_label)` | 계정 중복 등록 방지 |
| `Game` | `(source, external_id)` | 같은 RAWG 게임의 마스터 중복 등록 방지 |
| `Member` | `email` | 계정 중복 및 재사용 방지 |

> PK(id)는 행을 구분할 뿐 중복을 막지 않는다. **중복 방지의 최종 방어선은 DB 유니크 제약이다.** 애플리케이션 검증은 사용자 친화적 메시지를 위한 보조 수단이다.
>
> **소프트 삭제와의 충돌 (v1.3)**: 소프트 삭제된 행도 물리적으로 존재하므로 유니크 검사에 걸린다. 같은 값을 다시 만들면 유니크 위반이 난다. §7.4의 삭제 정책(되살리기 + 물리 삭제 혼합)이 이 충돌의 해소 방안이다.

### 7.4 삭제 정책 (v1.3 전면 개정)

> **v1.2의 "전 엔티티 소프트 삭제"를 폐기한다.** 두 가지 문제 때문이다.
> 1. **유니크 제약과 충돌**: 삭제된 행이 물리적으로 남아, 같은 값을 다시 만들면 유니크 위반이 난다. 예: 게임 삭제 후 재추가 → 409, 태그 `"명작"` 삭제 후 재생성 → 409
> 2. **마스터에 무의미**: `Game`을 소프트 삭제하면 전체 회원의 백로그 항목이 가리키는 대상이 숨겨져 깨진다. 마스터의 정리는 소프트 삭제가 아니라 병합(FR-ADM-02)의 몫이다

**엔티티별 삭제 방식**

| 엔티티 | 방식 | 근거 |
|---|---|---|
| `Member` | 소프트 → 유예 만료 시 배치 물리 삭제 | 탈퇴 유예(FR-AUTH-09). 유예 중 이메일 재사용 불가는 의도된 동작(BR-AUTH-02) |
| `BacklogEntry` | 소프트 + **되살리기(revive)** | 아래 되살리기 규칙 참조 |
| `PlatformAccount` | 소프트 + 되살리기 | 회차·취득이 참조하므로 보존(§6.5). 동일 라벨 재등록 시 되살리기 |
| `Tag` / `Genre` | **물리** | 미사용 시 자동 소멸이 스펙 자체(§6.7). 유니크 충돌 원천 차단 |
| `Playthrough` / `Acquisition` / `Subscription` | **물리** | 부모(항목/회원)가 소프트 삭제되면 함께 숨겨지므로 자체 `deletedAt` 불필요. 개별 삭제 이력은 스냅샷(§7.5)이 담당 — 단, `Acquisition`·`Subscription`은 스냅샷 대상이 아니므로 이력 없이 삭제됨을 감수한다 |
| `Game` / `Platform` / `Device` (마스터) | **삭제 없음** | 정리는 관리자 병합·마스터 관리(FR-ADM-02/04) |
| `CoverImage` | 물리 (스토리지 파일 포함) | §6.10 정리 규칙 |
| 스냅샷 / 감사 로그 | **삭제 없음** | 지워지지 않는 것이 존재 이유인 테이블 |

**되살리기(revive) 규칙 — `BacklogEntry`**

```
재추가 요청
 ├─ 살아있는 행 존재   → 409 (FR-BL-02)
 ├─ 삭제된 행 존재     → "이전 기록을 복원할까요?" 확인 → deletedAt = null
 │                       기존 평점·회차·취득 기록이 그대로 돌아온다
 └─ 없음               → 신규 INSERT
```

- 되살리기 시 백지로 밀지 않고 **기존 데이터를 복원**한다 (제품 결정)
- 단순 INSERT가 3단계 분기가 되는 비용을 감수한다 — 이것이 소프트 삭제의 실제 가격이다

**소프트 삭제 대상 엔티티의 공통 규칙**

- `deletedAt` 컬럼을 두고, 조회 시 `deletedAt IS NULL` 조건이 항상 적용되어야 한다
- **위험**: 조회 한 곳에서 조건을 빠뜨리면 삭제된 데이터가 노출된다. 엔티티 레벨 자동 적용(`@SQLRestriction`)을 검토하되, 조건이 코드에 드러나지 않는 부작용을 인지한다. 특히 **되살리기 경로는 삭제된 행을 조회해야 하므로** `@SQLRestriction` 사용 시 네이티브 쿼리 등 우회가 필요하다

**부분 유니크 인덱스는 채택하지 않는다**

PostgreSQL의 `WHERE deleted_at IS NULL` 부분 인덱스가 정석 해법이지만, H2가 미지원이라 개발/운영 DB의 제약이 갈라진다. Flyway 전환(Phase 9) 시점에 재검토한다.

### 7.5 변경 이력 (스냅샷 방식 — v1.3)

- 대상: `BacklogEntry`, `Playthrough` **한정**
- 기록 항목: 대상 타입, 대상 ID, **스냅샷 JSON(엔티티 상태 전체)**, 변경자, 변경 시각
- 직렬화 범위: 엔티티 자신의 필드만. 연관은 **ID만** 저장한다 (객체 그래프를 통째로 직렬화하지 않는다)
- 복원 규칙은 FR-BL-09 참조 — 검증 통과 시에만 커밋, 참조 소멸 시 실패, 복원 후 비정규화 재계산
- 관리자 행위에 대한 감사 로그는 별도다 (§6.12)

### 7.6 상태 파생 규칙

| 조건 | `status` |
|---|---|
| 회차 없음 + 취득 방식 `NOT_OWNED` | `WISHLIST` |
| 회차 없음 + 그 외 취득 | `BACKLOG` (쌓아둠) |
| 진행 중 회차 존재 | `PLAYING` |
| 최신 회차가 `PAUSED` | `PAUSED` |
| 최신 회차가 `DROPPED` | `DROPPED` |
| 최신 회차가 `COMPLETED` | `COMPLETED` |

계산 가능한 값이지만 §7.2에 따라 컬럼으로 저장한다.

**"최신 회차"의 정의 (v1.3)**: 회차 번호가 아니라 **날짜 기준** — `COALESCE(종료일, 시작일)`이 가장 늦은 회차.

- 근거: 과거 플레이를 뒤늦게 입력해도(특히 Obsidian 임포트) 상태가 과거 회차에 끌려가지 않는다. 회차 번호 기준이면 "2026년에 완료한 게임에 2025년 중단 회차를 나중에 추가"하는 순간 상태가 `DROPPED`로 뒤집힌다
- 진행 중 회차(종료일 null)가 있으면 위 표에 따라 어차피 `PLAYING`이 우선한다

### 7.7 금액과 통화

- 저장: 원본 통화 + 금액 (`Money` 값 타입)
- 통화는 **ISO 4217 코드 문자열**로 저장한다 (enum 미사용 — 확장성)
- 표시: 초기에는 원본 통화 그대로 표시한다. 환율 변환은 후속 단계에서 도입한다

**환율 적용 원칙 (도입 시)**

| 대상 | 처리 |
|---|---|
| 정가 | 실시간 환율로 변환 가능 (현 시점 기준 참고값) |
| 구매가 | **실시간 환율 변환 금지.** 구매 시점 환율을 스냅샷으로 저장 |

근거: 과거 구매액을 현재 환율로 변환하면 실제 지출이 왜곡된다.

- 환율은 **1일 1회만 조회하여 캐시**한다 (`@Scheduled` 배치)

> **NFR-S1 참고**: Spring Security의 `DelegatingPasswordEncoder`는 저장된 해시에 `{bcrypt}`, `{argon2}` 같은 접두어를 붙여 알고리즘을 식별한다. 따라서 나중에 알고리즘을 교체해도 기존 비밀번호를 폐기할 필요가 없다.

### 9.3 아키텍처

```
Controller   HTTP만 안다. DTO ↔ 서비스 호출
Service      트랜잭션 경계. 비즈니스 흐름 조율
Repository   JPA 직접 사용
Domain       비즈니스 규칙이 사는 곳
```

| ID | 요구사항 |
|---|---|
| NFR-A1 | 서비스 계층은 HTTP를 알지 못한다 |
| NFR-A2 | 의존성은 생성자 주입으로 받는다 |
| NFR-A3 | 엔티티를 API 응답으로 노출하지 않는다. DTO 변환은 트랜잭션 안에서 완료한다 |
| NFR-A4 | 규칙은 엔티티 안에 둔다 (도메인 모델 패턴). 서비스는 순서만 조율한다 |
| NFR-A5 | `@Transactional`은 클래스 레벨 `readOnly = true` + 쓰기 메서드에 개별 선언 |

### 9.4 운영

| ID | 요구사항 |
|---|---|
| NFR-O1 | 개발 전 기간 SQL 로그를 활성화한다 |
| NFR-O2 | 엔티티 안정화 후 Flyway를 도입하고 `ddl-auto: validate`로 전환한다 |
| NFR-O3 | **세션은 DB에 저장한다 (Spring Session + JDBC).** |

**NFR-O2 Flyway 도입 시점**
엔티티를 자주 수정하는 초기에는 `ddl-auto: create`가 훨씬 빠르다. **엔티티가 안정되고 배포가 임박한 시점에 전환한다.** Flyway는 DB 스키마 변경 이력을 SQL 파일로 관리하는 도구이며, `validate`는 하이버네이트가 스키마를 변경하지 않고 엔티티와의 일치 여부만 검사하게 한다.

**NFR-O3 세션 저장소**
Render 무료 티어는 인스턴스가 자주 재시작되어 **메모리 세션이 유실된다.** 재시작 시 전원 로그아웃되므로 Neon(PostgreSQL)에 세션을 저장하는 것이 사실상 필수다. Phase 9에서 적용한다.

| 구분 | 기술 |

#### 현재 의존성

추가 예정: Spring Security(Phase 3), `spring-boot-starter-restclient`(Phase 4), QueryDSL(Phase 6 / L-1 — Hibernate 7 호환 버전 확인 필요, 커뮤니티 포크 `io.github.openfeign.querydsl` 검토), Flyway(Phase 9)

#### 데이터 접근 규약 (v1.4 추가)

Spring Data JPA를 쓰되 `JpaRepository`를 직접 상속하지 않는다.

```
BaseRepository<T, ID>          findById · findAll · delete · persist  (save() 없음)
    └─ BaseRepositoryImpl      SimpleJpaRepository 상속 + persist 구현
         MemberRepository / GameRepository / BacklogEntryRepository
```

- **근거**: `SimpleJpaRepository.save()`는 내부가 `if (새 엔티티) persist else merge`다. 준영속 엔티티에 `save()`를 부르면 조용히 `merge()`가 돌아 §설계 원칙(변경 감지 우선, `merge()` 금지)을 어긴다. 인터페이스에서 `save()`를 빼면 **컴파일 단계에서** 막힌다
- 신규 저장은 `persist()`, 수정은 **변경 감지**, 벌크는 `@Modifying` + `@Query`
- `@EnableJpaRepositories(basePackages = "com.milobeene.gamebacklog", repositoryBaseClass = BaseRepositoryImpl.class)` — 이 애노테이션을 직접 달면 부트 자동 설정이 꺼지므로 `basePackages`를 반드시 명시한다

#### Spring Boot 4 주의사항 (v1.4 추가)

**참고 강의(JPA 활용편)는 Spring Boot 3.x 기준이므로 아래가 다르다.**

| 3.x | 4.x |
|---|---|
| `spring-boot-starter-web` | **`spring-boot-starter-webmvc`** |
| `spring-boot-starter-test` 하나 | **스타터마다 대응하는 `-test` 짝**을 따로 추가 |
| `h2` 의존성만으로 콘솔 동작 | **`spring-boot-h2console`** 별도 필요 |
| `org.springframework.boot.autoconfigure.*` | 모듈별 `org.springframework.boot.<기술>.*` |
| `RestTemplate` | Framework 7에서 deprecated → **`RestClient`** |

- **의존성을 추가할 때마다 `-test` 짝을 함께 넣는다.** 누락 시 `@DataJpaTest` 같은 애노테이션이 예외 없이 조용히 동작하지 않는다

## 10. 개발 단계

> 순서 결정 원칙: **(1) 뒤 단계가 앞 단계에 의존하는 순서, (2) 되돌리기 비용이 큰 결정을 먼저, (3) 학습 곡선이 가파른 것을 앞쪽에.**

> 전 단계에 걸쳐 §1.4의 개발 원칙(DP-1 ~ DP-5)이 적용된다.

> ### 졸업선 (v1.3)
>
> **Phase 7 완료 = 학습 목표 달성 (졸업). Phase 8~10은 보너스다.**
>
> - 근거: Phase 6까지 G-3의 학습 목표가 배포를 제외하고 전부 커버되고, Phase 7은 Phase 6의 실전 검증 지점이자 G-2(Obsidian 이전)의 완결 지점이다
> - Phase 8(프론트)은 주력 분야라 사실상 놀이, Phase 9(배포)는 보너스 1순위, Phase 10은 원래 선택 항목
> - 졸업선의 목적은 중단이 아니라, Phase 8부터를 "보너스를 하는 중"이라는 감각으로 진행하기 위함이다. 습작이 "또 하나의 미완성 프로젝트"가 되는 것을 막는 심리적 장치다

### Phase 0 — 도메인 설계 ✅ 완료 (2026-08-18)

- **진행 방식: 개발자가 직접 설계하고, 리뷰를 받는다 (DP-5).**
- 산출물: 엔티티 18개 코드, 필드/타입, 연관관계와 주인, 제약 조건 — `docs/entity-design-v0.2.md`
- **이 단계에서 결정을 최대한 확정한다.** 엔티티 구조는 되돌리기 비용이 가장 크다
- 선행 확인 필요: ~~OI-05, OI-06, OI-13~~ → OI-06·OI-13 해소, OI-05는 Phase 1로 이관

#### 검증 방식 (v1.4 — 실제 수행 기록)

`ddl-auto: create`로 실행해 **생성된 DDL을 눈으로 확인**하는 절차를 두었고, 코드 리뷰만으로는 잡히지 않는 문제 3건을 여기서 발견했다.

| 발견 | 내용 |
|---|---|
| `@AttributeOverride`는 병합이 아니라 **교체** | `Money`에 준 `precision`/`length`가 사라져 `numeric(38,2)`, `varchar(255)`가 됨 |
| enum이 **H2 네이티브 `enum` 타입**으로 생성 | Hibernate 6.2+ 기본 동작. `@JdbcTypeCode(SqlTypes.VARCHAR)`로 `varchar` + `check` 제약으로 전환 |
| `preferred_enum_jdbc_type` 전역 설정 미적용 | 애노테이션 방식이 확실. **전역 설정은 먹으면 편한 것, 애노테이션은 확실한 것** |

> **원칙**: 엔티티를 추가·수정할 때마다 DDL을 확인한다. 매핑 애노테이션의 실제 효과는 코드만 봐서는 알 수 없다.

### Phase 1 — 핵심 도메인 CRUD

`Member`(최소), `Game`, `BacklogEntry`, `Playthrough`, `Acquisition`, `Tag`, `Platform`, `PlatformAccount`, `Device`

- 엔티티, Repository, Service, 검증 규칙(BR-PT-01~05)
- 테스트 코드
- **웹 계층 없이 서비스 계층까지만.** 강의(활용 1편)와 동일한 순서
- 학습 초점: 연관관계, 트랜잭션 경계, 변경 감지, 도메인 모델 패턴

### Phase 2 — 웹 계층과 DTO

Controller, DTO 변환, 글로벌 예외 처리(`@RestControllerAdvice`)

- 학습 초점: 엔티티 미노출 원칙, 일관된 에러 응답, 서버 측 재검증

### Phase 3 — 인증/인가

폼 로그인, 세션, 이메일 인증, 비밀번호 재설정, Google OAuth 연결, 탈퇴 유예, 감사 로그

- **커버 업로드보다 앞에 배치한 이유**: 업로드는 "누가 올렸는가"를 전제한다. 소유권 개념이 없는 상태에서 파일을 다루면 나중에 전부 고쳐야 한다
- 학습 초점: Spring Security 필터 체인, 인증과 인가의 분리, 토큰 설계, 해시 알고리즘

### Phase 4 — RAWG 연동

검색, 온디맨드 캐시, 수동 등록, 재동기화, 장애 처리

- 학습 초점: 외부 API 클라이언트, 캐시 전략, 실패 처리, 키 관리

### Phase 5 — 커버 업로드

오브젝트 스토리지 연동, presigned URL, 검증, 정리

- 학습 초점: 파일 업로드 아키텍처, 서명 URL, 외부 스토리지 수명주기

### Phase 6 — 조회 성능과 통계

검색·필터·정렬·페이징, 비정규화 컬럼 갱신, N+1 대응, 통계 API

- **성능 작업을 뒤에 둔 이유**: 데이터와 쿼리가 있어야 문제가 눈에 보인다. 먼저 터뜨리고 고치는 편이 학습 효율이 높다
- 학습 초점: fetch join, batch size, 페이징 충돌, 인덱스

### Phase 7 — Obsidian 임포트

파일 업로드, YAML 파싱, 건별 트랜잭션, 실패 리포트

- **실데이터 투입 지점.** 여기서부터 Phase 6의 대응이 실제로 검증된다
- 학습 초점: 트랜잭션 분리, 프록시 자기호출 함정, 벌크 처리

### Phase 8 — 프론트엔드

Next.js 연동, 화면 설계, CORS/쿠키 처리

### Phase 9 — 배포

Flyway 전환, `ddl-auto: validate`, Neon/Render/Vercel 배포, Spring Session + JDBC, 환경변수

### Phase 10 — 선택 항목

스크린샷/영상, 환율 변환 배치, 관리자 화면 고도화

**범위**: `Member`(최소), `Game`, `BacklogEntry`, `Playthrough`, `Acquisition`, `Tag`, `Platform`, `PlatformAccount`, `Device`

**착수 순서**

1. **`Platform` / `Device` 시드 작성** — OI-05를 여기서 확정한다
2. **Repository** — `EntityManager` 직접 사용으로 시작. 스프링 데이터 JPA로의 번역은 나중에 before/after 대조로 학습
3. **Service** — `@Transactional(readOnly = true)` 클래스 레벨 + 쓰기 메서드 개별 선언 (NFR-A5)
4. **검증 규칙 구현** — BR-PT-01~05
5. **테스트 코드**

**Phase 1에서 반드시 구현할 것 (Phase 0에서 필드만 만들고 미룬 것)**

| 대상 | 내용 |
|---|---|
| `BacklogEntry.syncFromPlaythroughs()` | 최신 회차(§7.6) 기준으로 `status`·`lastPlayedOn` 재계산. 회차가 0개일 때 `WISHLIST`/`BACKLOG` 처리 포함 |
| 비정규화 갱신 (§7.2) | `displayName` 갱신 경로를 한 메서드로 모은다. `nameOverride` 변경 시, 관리자의 `Game.name` 수정 시 |
| 표시값 계산 (§5.2) | `오버라이드 ?? 마스터` 로직을 한 곳에만 둔다. 개발사·퍼블리셔는 **리스트**이므로 `isEmpty()` 기준 |
| BR-PT-03 | 진행 중 회차 1개 제한 — 서비스 계층 검증. **동시성은 보장되지 않음**(부분 유니크 인덱스 H2 미지원, §7.4) |
| 태그/장르 자동 소멸 | 연결 해제 후 COUNT → 0이면 DELETE (§6.7) |
| 역방향 컬렉션 | 필요해지는 시점에 `@OneToMany(mappedBy=...)` 추가. 미리 만들지 않는다 |

**학습 초점**: 연관관계, 트랜잭션 경계, 변경 감지, 도메인 모델 패턴

**진행 원칙**: DP-1~DP-5 유지. 코드는 직접 타이핑하고, SQL 로그를 켜둔 채 개발한다.
