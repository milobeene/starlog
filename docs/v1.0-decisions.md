## 🔴 먼저 정해야 하는 것

### Q1. 로그인을 없앨까, 남길까?

나 혼자 쓰는 앱이다. 지금은 이메일/구글 로그인 + 세션 + CSRF가 다 있다.

| | 뜻 | 딸려오는 것 |
|---|---|---|
| **A. 완전 제거** | 앱을 열면 바로 내 계정 | `LoginMemberArgumentResolver` 한 곳만 고치면 된다. 세션·CSRF·구글 OAuth·`(public)/` 화면 8개가 전부 무의미해진다 |
| **B. 비밀번호만 남김** | 앱을 열면 비번 한 번 | 노트북을 잃었을 때의 최소 방어. 대신 세션 비슷한 게 필요 |
| **C. 그대로** | 지금처럼 | 구글 OAuth를 루프백 흐름으로 새로 짜야 한다 (2-5) |

**내 추천: A.** 내 컴퓨터의 내 파일이고, 어차피 앱이 DB 자격증명을 들고 있어서
로그인은 보안이 아니라 형식이 된다. 노트북 자체를 FileVault로 잠그는 게 맞는 층위다.

### Q2. 프론트를 어떻게 서빙하고, 백엔드 주소를 어떻게 알려줄까?

`NEXT_PUBLIC_API_BASE`가 **빌드 시점에 굳는데** 일렉트론은 보통 포트를 실행 시점에 고른다 (2-1).
그리고 `/library/[entryId]` 때문에 정적 내보내기가 그냥은 안 된다 (2-3).

세 가지가 한 덩어리라 같이 정해야 한다.

| | 서빙 | 주소 전달 | 동적 경로 | 비고 |
|---|---|---|---|---|
| **A. Spring이 다 서빙** | Spring 정적 리소스 + SPA 폴백 | **필요 없음** (상대 경로) | 폴백이 해결 | **CORS·CSRF·쿠키 문제가 통째로 사라진다** |
| **B. 정적 파일 + 고정 포트** | 일렉트론이 파일 로드 | 포트 고정 | 경로를 쿼리로 바꿔야 함 | 가장 단순, 포트 충돌 위험 |
| **C. Next 서버를 앱 안에서** | `next start` | 런타임 주입 | 그냥 됨 | 프로세스 하나 더, 기동 느려짐 |

**내 추천: A.** 오리진이 하나가 되면서 2-1·2-2·2-3·2-4가 **한 번에 해결된다.**
Spring에 SPA 폴백 컨트롤러 하나 붙이는 게 전부다.

### Q3. 백엔드를 일렉트론에 어떻게 넣을까?

| | 앱 크기 | 기동 | 난이도 |
|---|---|---|---|
| **A. JRE 번들** | +150~180MB | 3~5초 | 쉬움 |
| **B. jlink 최소 런타임** | +50~70MB | 3~5초 | 중간 (모듈 목록을 뽑아야 함) |
| **C. GraalVM 네이티브** | +80MB | 0.1초 | **어렵다** — Hibernate·QueryDSL·Flyway 리플렉션이 고생길 |

**내 추천: A로 시작해서 나중에 B.** 혼자 쓰는 앱이라 200MB가 문제가 안 되고,
C는 이 스택에서 며칠을 태울 수 있다. **먼저 도는 걸 만들고 크기는 나중에 줄인다.**

### Q4. 웹 전용 코드를 **지울까, 끌까**?

실측 규모: **61파일 3,157줄** + 테스트 15파일 + 프론트 화면 8개 (main의 26%).
이미 `@Profile("!local-app")`과 `WEB-ONLY` 주석이 22개 파일에 붙어 있다.

- **지운다** — 코드베이스가 확 가벼워진다. 되돌리려면 git 이력에서 꺼내야 한다
- **끈다** — 프로파일 하나로 껐다 켰다. 안 쓰는 코드가 계속 눈에 밟힌다

**내 추천: 지운다. 단 웹을 실제로 내린 뒤에.** 웹이 살아 있는 동안 지우면 웹이 죽는다.

### Q5. 마이그레이션은 누가 올리나?

기계가 둘이라 버전이 어긋나면 앱이 안 뜬다 (2-7).

- **A. 둘 다 Flyway 켜둔다** — 먼저 뜬 쪽이 올린다. 어긋나면 나중 쪽이 실패
- **B. 한 대만 켠다** — 맥북이 주인, 윈도우는 `validate`만
- **C. 별도 CLI** — 스키마 올리는 건 앱과 분리

**내 추천: A + 읽히는 실패 메시지.** 기계가 둘뿐이라 규칙보다 안내가 낫다.
"스키마가 앞서 있습니다. 이 기계의 앱을 업데이트하세요" 정도.
